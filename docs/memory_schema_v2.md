**확정일** 2026-07-28 · **작업** `namu-65-memory-schema-unify` · **상태** **구현·배포 완료 (2026-07-31, v0.1.43)**

완료조건 15개 전부 충족. 로컬 두 곳(claude·agy)과 웹 원격(namu.onnamu.kr) 모두 v0.1.43이며,

## 1. 왜 고치나

### 발단

웹 채팅에서 조사 자료 원문을 `bowl='learnings'`로 저장했는데 **본문이 통째로 사라졌다.**
`namu_record`에 `text` 항목이 노출돼 있지만, learnings 경로에서는 그 값을 저장 계층에
넘기지 않아 **말없이 버려진다.**

처음에는 "learnings에 `text`를 넘기면 거절하자"는 좁은 가드로 처리하려 했다.
실제 데이터를 세어보고 그 처방이 **결함을 고치는 게 아니라 코드로 못 박는 것**임이 드러났다.

### 실측 (2026-07-28)

| 그릇 | 건수 | 측정 결과 |
|---|---|---|
| learnings | 157건 | `reason` 100자 이하(원 설계 의도)는 **8건뿐**, 1,000자 초과 **43건**, 최대 **2,079자** |
| profile | 8건 | `statement` 최대 582자. **`text`를 넘기면 learnings와 똑같이 말없이 버려진다** |
| tasks | 450줄 | `[다음]` 줄 48개 중 **41개가 300자 초과**, 최대 **2,081자** |
| memo | 1장 | 원문 보관이 목적이라 이상 없음 |

### 진단

**한 칸이 "요약"과 "상세" 두 일을 겸하도록 설계된 것이 원인이다.**

157건 중 149건이 의도를 벗어났다는 것은 규율이 무너진 게 아니라 **지킬 수 없는 설계**였다는 뜻이다.
상세를 적을 자리가 없으니 전부 한 칸으로 밀려들어왔다.

그 결과 이 데이터를 읽는 모든 곳이 둘 중 하나를 해야 했다.

1. 글 벽을 그대로 쏟는다 (세션 시작 브리핑)
2. AI가 화면에 띄울 때마다 요약을 새로 지어낸다 (`/namu` 출력)

2번이 특히 나쁘다. **요약한 주체가 그 일을 겪지 않은 나중 세션의 AI**라서 짐작이 섞이고, 볼 때마다 달라진다.

### 파급

`namu-62` · `namu-63` · `namu-64`가 세 세션에 걸쳐 고친 "브리핑 가독성"은
**여기서 새는 물을 화면에서 걸레질한 것**이었다. 문장 단위 줄바꿈, 항목 강조,
잘림 방지 — 전부 한 칸에 2,000자가 들어온다는 전제 위의 대응이었다.

> **교훈** 화면 서식을 반복해서 고치고 있다면 데이터 구조를 의심하라.

## 2. 설계 원칙 (사용자 확정)

| # | 원칙 |
|---|---|
| 1 | **메소드는 `namu_record` 하나만.** 새 메소드를 만들지 않는다 |
| 2 | **네 그릇 전부 `summary` · `reason` · `body` 3층을 갖고, 셋 다 필수.** 예외 없음 |
| 3 | 적을 게 없으면 **`생략`** 한 단어를 넣는다 (화면에서는 감춘다) |
| 4 | 그릇에 없는 칸이 들어오면 **조용히 버리지도, 아무거나 받지도 않는다** — 즉시 거절하고 어느 그릇으로 가야 하는지 알려준다 |
| 5 | 파라미터 이름을 네 그릇에서 **같은 뜻으로 통일**하고, **항목마다 개별 설명**을 단다 |

### 원칙 4에 대하여

유실을 막는 방법이 "전부 허용"이면 그건 스키마를 포기한 것이다.
네 그릇이 같은 칸을 전부 받아주면 **그릇을 나눈 이유가 사라진다.**

가능한 선택은 셋뿐이고, 옳은 것은 하나다.

- ❌ 조용히 버리기 — 이번 사고의 원인
- ❌ 아무거나 받기 — 그릇 구분 파괴
- ✅ **거절하고 갈 곳을 알려주기**

### 원칙 2에 대하여 — `reason`은 재검토 대상이 아니다

`reason`을 필수로 두는 근거는 "판단 근거가 없으면 다음 세션이 결론만 보고 왜 그랬는지 모른다"는 것이다.

기존 tasks 450줄에 `reason`이 없는 것은 **칸 자체가 없었기 때문이지 불필요해서가 아니다.**
이를 "규칙이 과했다"의 근거로 삼는 추론은 잘못이다.

## 3. 3층 구조

| 층 | 이름 | 답하는 질문 | 길이 |
|---|---|---|---|
| 1층 | `summary` | **무엇을?** | 한 문장 |
| 2층 | `reason` | **왜?** | 짧은 문단 |
| 3층 | `body` | **그때 무슨 일이?** | 무제한 |

세 층이 서로 다른 질문에 답하므로 경계가 흐릿하지 않다.

### 그릇별로 채워지는 모습

| 그릇 | `summary` | `reason` | `body` |
|---|---|---|---|
| **교훈** (learnings) | 배운 것 한 줄 | 왜 그런가 | 그때 무슨 일이 있었나 |
| **개인 사실** (profile) | 사실 한 줄 | 어떻게 알았나 (옛 `source`) | 배경·경위 |
| **작업일지** (tasks) | 진행 상황 한 줄 | 왜 그렇게 판단했나 | 상세·인수인계 |
| **쪽지** (memo) | 메모 한 줄 | 왜 남기나 | 원문 그대로 |

실제 사례 (2026-07-28 이커머스 조사 쪽지)

```
summary: 이커머스 가격 자동 매칭 프로그램 조사 자료
reason : 지인 프로그램 제작 검토용
body   : (조사 내용 전문)
```

### 칸별 설명

- **`summary`** — 한 줄 요약(무엇을?). 브리핑·목록 화면에 그대로 실리는 유일한 칸이라, 일을 한 AI가 저장 시점에 한 번 쓰고 고정한다 — 나중 세션이 볼 때마다 새로 지어내던 요약이 매번 달라지던 문제를 여기서 끊는다.
  - 예) `브리핑 가독성 수정은 데이터 구조 결함을 화면에서 걸레질한 것이었다`
- **`reason`** — 왜 그런가 / 어떻게 알았나 / 왜 남기나(짧은 문단). 결론만 남기면 다음 세션이 판단 근거를 알 수 없어 같은 논의를 되풀이한다.
  - 예) `한 칸이 요약과 상세를 겸해 157건 중 149건이 원 의도를 벗어났기 때문`
- **`body`** — 그때 무슨 일이 있었나 — 원문·경위 전부(길이 제한 없음). 쪽지에서는 붙여둔 원문 자체가 여기 들어간다. 이 칸이 없어서 웹에서 저장한 조사 원문이 통째로 사라졌다.
  - 예) `(조사 자료 전문·재현 절차·측정값 등 원문 그대로)`
- **`bowl`** — 어느 그릇에 담을지. 생략할 수 없다 — 안 적으면 거절하고 네 그릇을 안내한다. 교훈(learnings)은 다시 쓸 배움, 개인 사실(profile)은 사용자에 대한 사실, 작업일지(tasks)는 진행 기록, 쪽지(memo)는 쓰고 버릴 메모다.
  - 예) `memo`
  - 쓸 수 있는 값: `learnings` · `profile` · `tasks` · `memo`
- **`topic`** — 주제·작업 이름. 교훈은 어느 작업에서 얻었는지, 개인 사실은 무엇에 대한 사실인지(옛 subject), 작업일지는 어느 작업의 log.md에 붙일지를 정한다 — 작업일지에서는 이미 있는 작업의 이름이나 그 앞부분이어야 한다. 쪽지는 받지 않는다(쓰고 버리는 그릇이라 분류할 이유가 없다).
  - 예) `namu-65-memory-schema-unify`
- **`status`** — 상태. 교훈은 success/failure/partial 셋 중 하나이며, 비면 교훈이 아니라 단순 기록으로 취급한다(옛 kind를 대신하는 판정 기준). 작업일지는 줄 앞에 붙는 꼬리표이고 기본값은 '기록'이다. 개인 사실·쪽지는 받지 않는다. 주의: 작업일지의 '완료'/'중단'은 **작업 전체가 닫힌다**는 뜻이라 진행 메모에 쓰면 열린 작업 목록에서 사라진다(실제 사고 2회). 반대로 '종료'·'마무리' 같은 비슷한 말은 **닫지 못하므로 거절한다** — 닫는 말은 이 둘뿐이다(namu-66).
  - 예) `failure`
  - 교훈에서 쓸 수 있는 값: `success` · `failure` · `partial`
- **`category`** — 갈래. 생략하면 other. 교훈 전용이다(옛 task_type).
  - 예) `code`
  - 쓸 수 있는 값: `code` · `doc` · `analysis` · `other`
- **`tags`** — 꼬리표 목록. 개인 사실에 '상시'를 붙이면 세션 시작 1회가 아니라 사용자 입력마다 다시 올라온다. 작업일지는 받지 않는다 — 거기서 꼬리표에 해당하는 것은 status다.
  - 예) `['상시', '출력규칙']`
- **`project`** — 프로젝트 폴더 이름. 작업일지 전용이다. 로컬에서는 생략하면 현재 폴더로 보지만, 웹에는 현재 폴더라는 것이 없으므로 반드시 적어야 한다.
  - 예) `namu-agent`
- **`confidence`** — 이 내용을 사람이 확인했는지, AI 판단인지(옛 verified_by). 나중에 신뢰도로 거르기 위한 칸이라 짐작을 human으로 적으면 안 된다.
  - 예) `human`
  - 쓸 수 있는 값: `human` · `ai` · `unverified`
- **`supersedes`** — 정정할 옛 기록의 id. 개인 사실은 고쳐 쓰지 않고(append-only) 새 항목이 옛 항목을 가리키는 방식으로 정정한다.
  - 예) `01KYKFDR8Q2N7V0C6W3M5Y1XT`
- **`create`** — 참이면 새 작업 폴더를 만든다. 거짓(기본)일 때 없는 작업 이름을 주면 만들지 않고 후보를 들어 거절한다.
  - 예) `True`
- **`done_when`** — 완료조건 목록. 작업을 새로 만들 때(create) 체크리스트로 적힌다.
  - 예) `['입력 항목이 13개로 정리된다', '기존 테스트 386개 통과']`

### 옛 이름 → 새 이름

| 옛 이름 | 새 이름 | 어느 그릇에서 | 비고 |
|---|---|---|---|
| `task` | `topic` | 모든 그릇 | 교훈의 작업 이름 |
| `subject` | `topic` | 모든 그릇 | 개인 사실의 주제 |
| `statement` | `summary` | 모든 그릇 | 한 줄은 summary, 상세가 있으면 body로 나눠 넣는다 |
| `source` | `reason` | 모든 그릇 | '어떻게 아는가'라 2층(reason)이 맞다 |
| `outcome` | `status` | 모든 그릇 |  |
| `tag` | `status` | 작업일지(tasks) | 작업일지 꼬리표 |
| `text` | `summary` | 작업일지(tasks) | 작업일지의 한 줄 |
| `text` | `body` | 교훈(learnings)·개인 사실(profile)·쪽지(memo) | 옛 경로에서 말없이 버려지던 원문 — body로 살린다 |
| `task_type` | `category` | 모든 그릇 |  |
| `verified_by` | `confidence` | 모든 그릇 |  |
| `kind` | (없앰) | 모든 그릇 | 없앴다 — status가 있으면 교훈, 없으면 단순 기록으로 본다 |
| `title` | `summary` | 작업일지(tasks) | 작업을 새로 만들 때 |
| `purpose` | `reason` | 작업일지(tasks) | 작업을 새로 만들 때 |

옛 이름으로 호출해도 **새 이름으로 옮겨 저장하고, 어디로 옮겼는지 반환문에 알린다.** 말없이 버리는 경로는 코드에 없다.

**초안에서는 "고치지 않는다"였으나, 사용자 결정으로 뒤집혔다.**
구현에 들어가기 **직전에 데이터 옮기기를 먼저 수행**한다.

| 대상 | 처리 |
|---|---|
| 교훈 157건 | `reason` 한 덩어리를 **읽고 `summary` / `reason` / `body`로 나눠 넣는다** |
| 개인 사실 8건 | `statement`를 `summary` / `body`로, `source`를 `reason`으로 옮긴다 |
| 작업일지 450줄 | 줄 뒷부분을 `summary` / `reason` / `body` 세 줄 묶음으로 나눈다 |
| 옛 이름으로 오는 호출 | 새 이름으로 옮겨 저장하고 어디로 갔는지 알린다 |
| 검색 캐시 | 칸 변경을 자동 감지해 재생성 (`db.cache_is_stale` — 이미 있음) |

### append-only 원칙의 명시적 예외

`learnings.yaml`과 `log.md`는 **수정·삭제하지 않는다**가 개발 원칙 3이다.
이 마이그레이션은 그 원칙을 한 번 깨는 작업이므로, 아래 안전장치를 조건으로 건다.

| # | 안전장치 |
|---|---|
| 1 | 실행 전 **원본 전체를 통째로 백업**한다 (`~/.namu/memory/*.yaml`, `~/.namu/tasks/`) |
| 2 | 마이그레이션은 **한 번의 독립 커밋**으로 남긴다 — 되돌리기 지점이 명확해야 한다 |
| 3 | **글자 보존 검사** — 나눈 세 칸을 도로 이으면 원본과 같아야 한다. 한 글자도 사라지지 않는다 |
| 4 | 건수 검사 — 옮긴 뒤 항목 수가 옮기기 전과 정확히 같아야 한다 |
| 5 | 먼저 **일부(10건)만 옮겨 사용자 확인**을 받고 나머지를 돌린다 |

### 나누는 주체

`summary`는 기계적으로 뽑을 수 없다 — 첫 문장을 자르는 방식은 요약이 아니다.
**AI가 각 항목을 읽고 한 줄로 정리한다.** 157건 + 8건 + 450줄이므로
**한 번에 다 하지 말고 묶음으로 나눠 돌린다** (한도 소진 위험).

**범위 밖** — 대시보드 화면.

## 8. 완료조건

1. 입력 항목이 19개 → 13개로 정리되고, 같은 이름이 네 그릇에서 같은 뜻으로 쓰인다
2. 항목마다 개별 설명이 붙는다 — ①어느 그릇에서 필수인지 ②어느 그릇에서 쓰면 안 되는지 ③예시 한 줄
3. 옛 이름으로 호출해도 새 이름으로 옮겨 저장되고, 어디로 옮겼는지 반환문에 적힌다
4. 네 그릇 모두 3층을 갖고 전부 필수, 비면 거절
5. `생략` 한 단어를 허용하고, 화면에서는 그 줄을 감춘다
6. 그릇에 없는 칸을 넣으면 거절하고 어느 그릇으로 가야 하는지 알려준다
7. **조용히 버리는 경로가 코드에 하나도 남지 않는다** — 테스트로 보증
8. 거절 메시지는 무엇이 잘못됐고 어떻게 고치는지 한 문장으로 말한다
9. `log.md`가 세 줄 묶음으로 넓어지고, append-only 유지, 옛 450줄도 그대로 읽힌다
10. 브리핑에는 `summary`만 실린다
11. 검색이 `summary`·`reason`·`body` 세 칸 모두 훑는다
12. **구현 전에 데이터 옮기기를 먼저 끝낸다** — 원본 백업, 독립 커밋, 글자 보존 검사, 건수 검사, 10건 선행 확인 다섯 가지를 지킨다
13. 검색 캐시가 칸 변경을 자동 감지해 재생성한다
14. 기존 테스트 386개 전부 통과 + 신규 테스트 추가
15. 웹(stateless HTTP)에서도 동일하게 동작한다

## 9. 이 설계가 막는 것

| 사고 | 새 구조에서 |
|---|---|
| 원문을 잘못된 그릇에 넣어 유실 | 거절 + 갈 곳 안내. 글이 사라지지 않는다 |
| 브리핑에 2,000자가 쏟아짐 | `summary` 한 줄만 실린다 |
| AI가 볼 때마다 요약을 새로 지어냄 | 일을 한 AI가 저장 시점에 한 번 쓰고 고정된다 |
| 같은 결함이 옆 그릇에서 재발 | 그릇별 허용 칸 선언 한 곳에서 파생 |
