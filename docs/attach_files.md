# 첨부 파일 주고받기 — 나무 본체 몫 (완료 보고서)

**작업**: `namu-file-upload-download` · **상태**: 완료 (2026-08-07)
**작성**: 2026-08-08 — 만들어진 뒤에 쓴 문서다. "이렇게 만들 것이다"가 아니라
**"지금 무엇이 어떻게 도는가"**를 적는다.
**짝 문서**: 클라우드 몫은 `namu-cloud-routing/docs/namu_attach_files.md`.
이 문서는 나무 본체(터미널에서 쓰는 플러그인)만 다룬다.

> **왜 이 문서가 필요했나**
> 이 기능에는 설계서가 둘 있었는데 어느 쪽도 완성된 모습을 담고 있지 않다.
> 설계서 2판(쪽지 `01KZARD3XHRDET8MNKB6519T9Q`)에는 **티켓이 한 글자도 없다**
> (2026-08-08 확인: '티켓' 0회 · 'ticket' 0회 · '링크' 0회). 티켓 설계는 구현 도중
> 웹 세션에서 나왔고, 코드가 "설계서 5-4절 / 6-2절 / 7절"을 인용하는데
> **그 원문은 우리 기록 어디에도 없다**(다섯 그릇 전부 검색 확인). 즉 지금 이
> 기능을 설명하는 것은 코드와 그 주석뿐이었다. 이 문서가 그 자리를 메운다.

---

## 1. 한눈에

대화 중 만들거나 손에 든 파일을 회원 본인의 GitHub 저장소에 그대로 올리고,
나중에 그 하나만 다시 받는다. 세 가지가 이 기능의 뼈대다.

| 뼈대 | 무엇 |
|---|---|
| **파일은 회원 저장소로 간다** | 나무 서버나 개발자 서버에 사본을 두지 않는다 |
| **첨부 폴더는 각 PC에서 격리된다** | 파일 몸통이 회원의 여러 PC로 안 내려온다 |
| **이력은 모든 PC에 있다** | "무슨 파일이 있고 왜 올렸나"는 어디서나 답한다 |

파일 실물은 저장소의 `attach_file/` 한 칸에 평평하게 놓인다(하위 폴더 없음).
이력은 첨부 기록 그릇(`~/.namu/memory/attachments.yaml`)에 쌓인다.

## 2. 도구 일곱 개

| 도구 | 하는 일 | 알아둘 것 |
|---|---|---|
| `namu_upload_file` | 파일 하나를 올리고 이력을 남긴다 | 파일 경로 또는 글자 원문 **둘 중 하나**를 준다. 경로가 있으면 언제나 경로 쪽이 낫다 — 파일이 AI의 출력을 안 거친다 |
| `namu_list_files` | 올린 파일 목록 | 크기는 **첨부 기록에서 읽는다.** 저장소에 물으면 안 된다(4절) |
| `namu_download_file` | 파일 하나를 받는다 | 받은 일은 기록하지 않는다 |
| `namu_delete_file` | 파일 하나를 저장소에서 뺀다 | 왜 뺐는지가 필수. **완전 삭제가 아니다**(7절) |
| `namu_create_upload_ticket` | 올릴 수 있는 일회용 주소를 만든다 | 그림·PDF 같은 것과 100KB 넘는 것은 이쪽 |
| `namu_create_download_ticket` | 내려받을 주소를 만든다 | 회원에게 파일을 건네는 방법 |
| `namu_check_ticket` | 파일이 도착했는지 본다 | 회원이 "올렸어"라고 할 때 |

설계서 2판에는 도구가 셋(올리기·목록·받기)뿐이었다. 넷째로 지우기가, 그 뒤
티켓 셋이 붙어 일곱이 됐다. 왜 늘었는지는 8절.

## 3. 저장소를 다루는 방법 — 전부 git 명령이다

터미널은 회원 본인의 `~/.namu` 사본이 이미 그 저장소에 연결돼 있으므로 git으로
바로 다룬다(클라우드는 GitHub API를 쓴다 — 그쪽 문서 참고). 첨부 폴더가 격리돼
있어서 평범한 명령이 통하지 않는다. 아래는 2026-08-07에 실제 git으로 재서 정한
것이다.

| 하는 일 | 명령 | 왜 이 형태인가 |
|---|---|---|
| 올리기 | `git add --sparse` → commit → push → `sparse-checkout reapply` | 그냥 `add`는 "격리 밖"이라며 조용히 무시된다 |
| 목록 | `git ls-tree -r --name-only -z HEAD` | 이름만 묻는다. `-z`가 없으면 한글 이름이 깨져 지우기가 실패한다 |
| 받기 | `git cat-file blob HEAD:<경로>` | 몸통 없는 사본에서도 그 하나만 끌어온다(파일당 증가 0~12KB) |
| 지우기 | `git rm --sparse` → commit → push | |

올린 뒤 마지막에 격리를 다시 거는 것이 핵심이다 — 안 하면 방금 올린 파일이 그
PC에 남아 격리가 한 칸씩 무너진다.

## 4. 급소 — 크기를 저장소에 물으면 안 된다

**이 기능에서 가장 조심할 곳이다.**

목록을 만들 때 크기까지 함께 묻는 형태(`git ls-tree -l`)를 쓰면, git이 크기를
알아내려고 **빠진 파일 몸통을 전부 내려받는다.** 2026-08-07 실측에서 파일
2,548개에 7분이 넘도록 끝나지 않아 중단했다. 이름만 묻는 형태는 즉시 끝난다.

그래서 **크기는 첨부 기록의 `bytes` 칸에서만 읽는다.** 이 칸이 "있으면 좋은
정보"가 아니라 필수인 이유가 이것이다. 올릴 때 한 번 적어 두고, 이후로는 저장소에
되묻지 않는다.

되돌릴 수 없는 종류의 실수다 — 한 번 내려온 파일은 격리를 다시 걸어도 그 PC에서
안 사라진다.

## 5. 첨부 기록 그릇

다섯 번째 그릇으로 새로 만들었다. 칸 구성은 `docs/memory_schema_v2.md` 4장이
원본이므로 여기서 되풀이하지 않는다. 이 그릇만의 성질 세 가지만 적는다.

**① 지금 살아 있는 파일 목록은 계산해서 얻는다.** 기억은 고칠 수 없으므로 같은
파일에 `올림` → `새 판` → `지움`이 차곡차곡 쌓인다. 경로별 마지막 기록을 보고
그것이 `지움`이면 뺀다.

**② 지운 파일도 기록은 남는다.** "그 자료 어디 갔지?"에 "언제 뺐고 이유는 이것"
이라고 답하기 위해서다. 그래서 지우기 도구는 이유를 반드시 받는다.

**③ 받기는 기록하지 않는다.** 파일 자체가 달라지지 않는 일이고, 회원이 실제로
손에 넣었는지까지는 알 수 없어 반쪽만 남는다. 반쪽짜리 기록은 "받은 적 없다"로
잘못 읽힌다.

## 6. 티켓 — 파일 몸통이 AI를 거치지 않는 길

**왜 만들었나.** 파일 내용을 글자로 실어 보내면 붙은 AI가 그것을 **한 자씩 써야**
한다. 6KB짜리 문서 하나가 8,100자였고, 서버가 7.4초 걸리는 동안 AI 쪽이 몇 분을
썼다(2026-08-07 실측). 수 MB짜리는 이 방식으로는 사실상 못 다룬다.

**어떻게 도나.** AI는 "이 이름으로 파일 하나를 받겠다"는 약속만 만들고, 파일
몸통은 회원의 브라우저나 AI의 `curl`이 그 주소로 직접 던진다. AI의 출력을 한
글자도 거치지 않는다.

주소는 두 가지다 — 올리기 `/u/<티켓>`, 받기 `/d/<티켓>`. 올리기는 두 시간,
받기는 한 시간 뒤 만료되고 올리기는 한 번 쓰면 닫힌다.

**개인 주소에서도 그대로 동작한다.** 이 PC의 나무 서버(기본 `127.0.0.1:8765`)가
같은 주소 세 개를 연다. 티켓을 만드는 코드와 주소를 여는 코드는 클라우드와
**같은 파일 한 벌**이며, 저장할 자리와 화면 껍데기만 인자로 갈린다.

지켜지는 것 넷:

1. **티켓을 만드는 것만으로는 저장소에 아무것도 안 쓴다** — 안 쓰고 버려진
   티켓은 흔적을 안 남긴다.
2. **티켓 번호는 예측할 수 없다** — 256비트 난수다. 나무가 다른 곳에서 쓰는
   ULID를 여기서는 안 쓴다(앞부분이 만든 시각이라 이웃 번호를 좁힐 수 있다).
3. **번호 전체를 로그에 안 남긴다** — 로그를 보는 사람이 남의 티켓에 그대로
   들어갈 수 있게 되기 때문이다.
4. **메모리가 아니라 파일에 둔다** — 서버를 다시 띄워도 발급해 둔 링크가 살아
   있어야 한다. 기억 캐시에 같이 담지 않는 이유는 그 파일이 통째로 다시
   만들어지는 사본이라, 다시 만드는 순간 티켓이 함께 날아가기 때문이다.

## 7. 회원에게 반드시 알려야 하는 것

**지우기는 완전 삭제가 아니다.** git은 과거 이력을 남기므로, 지우기 전 시점으로
거슬러 올라가면 그 파일은 그대로 있다. 진짜로 지우려면 저장소 이력을 다시 쓰는
별개의 작업이 필요하고 이 기능의 범위 밖이다. 도구 설명문에도 이 사실이 적혀 있다.

## 8. 설계에서 바뀐 것과 왜 (설계 판단 요약)

| 항목 | 설계서 2판 (08-06) | 지금 | 왜 바뀌었나 |
|---|---|---|---|
| 도구 수 | 3개 | 7개 | 아래 두 줄 |
| 지우기 | 없음 | 있음 | 2판에는 `지움` 상태만 있고 그 상태를 만들 기능이 없었다. 상태는 있는데 쓸 방법이 없는 빈칸이었다 |
| 티켓 | **없음** | 3개 | 글자로 실어 보내는 방식이 크기에 정비례해 느려지는 것이 실측으로 드러났다. 6KB에 몇 분이면 발표자료·PDF는 못 다룬다 |
| 크기 상한 | 정하지 않음 | 20 MiB | 2판은 "재보기 전에 숫자를 박으면 문서가 못 지킬 약속을 한다"며 미뤘다. 도구를 만든 뒤 실제로 재서 채웠다 |
| 목록의 크기 | 저장소에 묻는다 | 첨부 기록에서 읽는다 | 4절. 2판의 근거가 된 재현이 세 줄만 받고 끝난 것이었다 |
| 올리는 방법 | 파일을 글자로 바꿔 실어 보냄 | 경로를 주거나 티켓 | 같은 이유(티켓 줄) |

**바뀌지 않은 것** — 파일은 GitHub과 직접 오간다 · 저장소는 하나로 두고
`attach_file` 폴더만 격리한다 · 첨부 기록 그릇을 따로 둔다 · 웹과 터미널 양쪽에서
쓴다. 2판의 골격은 그대로 섰다.

## 9. 크기 상한

기본 20 MiB이고 환경변수 `NAMU_ATTACH_MAX_BYTES`로 바꾼다. **터미널과 클라우드가
같은 이름의 환경변수, 같은 기본값을 쓴다** — 두 경로가 다른 상한을 쓰면 "여기서는
올라가는데 저기서는 안 올라간다"가 되고 회원에게 설명할 방법이 없다.

실측값과 그 한계는 클라우드 문서 쪽에 있다(운영 서버에서 쟀다).
