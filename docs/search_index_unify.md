## 1. 한 줄 목적

지금은 그릇마다 조회 방식이 달라 교훈만 색인을 타고 나머지 넷은 매번 파일을 통째로 읽는다.
**다섯 그릇을 모두 SQLite 색인으로 통일해 조회 경로를 하나로 만든다.**

## 2. 왜 하는가 (확정된 근거)

사용자가 밝힌 판단 근거는 **성능이 아니라 통일성**이다 — "교훈만 색인처리 되었고 나머지는
각각의 파일을 끌고 다니며 통으로 조회한다. 전체를 색인해 SQLite로 검색하는 것이 통일성
있고 이후까지 효율적이다."

이 진단은 코드와 일치한다(2026-08-03 실측):

| 그릇 | 지금 읽는 방식 | 코드 |
|---|---|---|
| 교훈(learnings) | SQLite + FTS5(trigram) | `db.py:40` |
| 작업일지(tasks) | log.md 78개를 매 질의마다 열어 합침 | `db.py:552` → `task_resolve.journal` |
| 개인 사실(profile) | profile.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:606` |
| 쪽지(memo) | memo.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:572` |
| 첨부 기록(attachments) | attachments.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:616` (2026-08-08 추가, 9장) |

## 4. 확정된 결정

1. **다섯 그릇 전부 SQLite 색인 대상**으로 한다. (2026-08-08 개정 — 08-03 원문은 "네 그릇".
   첨부 기록 그릇을 넣을지는 `namu-file-upload-download`에서 "범위 밖"으로 미뤄 둔
   항목이었고, 이 문서가 그 결정을 넘겨받는다. 상세는 9장.)
2. **원본은 파일 그대로 둔다** — learnings.yaml / profile.yaml / memo.yaml / log.md /
   attachments.yaml.
   색인은 재생성 가능한 사본이며, 개발 원칙 2("원본이 곧 기억")를 그대로 유지한다.
   → 파일 읽기가 없어지는 게 아니라 **질의 시점에서 동기화 시점으로 옮겨간다.**
3. **쪽지는 자기 색인표를 갖는다** — 교훈 색인에 합치지 않는다.
   namu-56이 금지한 것은 "교훈 검색 색인에 섞이는 것"이지(`db.py:574` 주석 원문)
   색인을 갖는 것 자체가 아니다. 별도 표면 그 결정과 충돌하지 않는다.
4. **두 글자 우회는 필수** — 5장 참고. 안 넣으면 지금보다 나빠진다.
5. 검색 결과는 **지금과 같아야 한다** — 6단계에서 옛 경로와 대조 검증.

## 5. 두 글자 우회 (반드시 함께 들어갈 것)

trigram 색인은 글을 세 글자씩 겹쳐 잘라 저장한다. 검색어도 같은 방식으로 잘라 맞추므로
**두 글자 이하 검색어는 자를 조각이 없어 0건이 된다.** 실측:

```
색인 내용: "이 문서는 검색 인덱스 설계에 관한 것이다"
  '설계'   → 0건      '인덱스' → 1건
  '검색'   → 0건      '설계에' → 1건
```

우리말 기술용어는 두 글자가 가장 흔하다(설계·검색·기억·작업·문서·배포·캐시).
**지금은 파이썬 부분일치라 잘 찾히므로, 우회 없이 색인으로 바꾸면 검색 품질이 퇴행한다.**

**우회 방법**: 검색어가 3자 미만이면 색인을 건너뛰고 `LIKE` 전수 조회로 폴백한다.
교훈이 이미 이 구조다(`db.py:328` — `if len(q) >= 3:` 분기, else LIKE). 나머지 셋에
같은 규칙을 적용하면 되고, 새로 발명할 것은 없다.

## 6. 작업 단계 (다음 세션은 여기부터)

### 1단계 — 저장표와 색인 만들기
- `db.py:20` `_SCHEMA`에 tasks / memo / profile / **attachments** 표 + 각 `_fts`
  가상표(trigram) + 트리거 추가.
- 쪽지 표는 **교훈 색인과 별도**(결정 3).
- 첨부 기록 표의 단위는 **파일 하나가 아니라 기록 한 건**이다 — 같은 파일에
  올림 → 새 판 → 지움이 여러 줄로 쌓인다. 자세한 칸 구성은 9장 2절.
- 표 설계 주의: 작업일지의 단위는 "레코드"가 아니라 **log.md 한 줄**이다
  (`ts / project / task_slug / tag / machine / via / text / detail`).
  `task_resolve._parse_log_line`(`task_resolve.py:683`)이 이미 이 형태로 파싱한다.

### 2단계 — 원본 파일을 표에 채우기
- `db.py:153` `rebuild_from_yaml`이 교훈용 단일 구현이다. 그릇별 ingest로 일반화한다.
- 입력원: `task_resolve.journal`(`task_resolve.py:724`), `memo.load_all`(`memo.py:33`),
  `profile.active`(`profile.py:105`), **`attachments.load_all`(`attachments.py:103`)**.
- 3층 텍스트는 각 그릇의 `layers()` 헬퍼를 쓴다(`memo.py:94`, `profile.py:83`) —
  옛 형식 항목도 같은 헬퍼가 돌려주므로 검색에서 빠지지 않는다.
- ⚠ **첨부 기록에는 `layers()` 헬퍼가 아직 없다**(2026-08-08 확인 — `attachments.py`에
  있는 것은 `load_all`·`current_files`·`history` 셋뿐이다). 이 단계에서 만들어야 한다.
- ⚠ **첨부 기록의 입력원은 `attachments.yaml` 하나뿐이다.** 파일 목록이나 크기를
  사용자 저장소에 물어 보완하려 들면 안 된다 — 이유는 9장 3절(격리).

### 3단계 — "색인이 낡았나" 판정을 그릇마다 정하기
- 지금 판정(`db.py:198` `cache_is_stale`)은 **교훈 전용**이다: ①스키마 컬럼 검사
  ②yaml의 `id:` 줄 수 vs db 행 수.
- 그대로는 안 통하는 이유:
  - **작업일지** — 원본이 파일 78개다. 한 파일의 줄 수 세기로는 부족하고,
    파일 목록 + 각 파일 크기·수정시각 또는 전체 줄 수 합계가 필요하다.
  - **쪽지** — 유일한 mutable 그릇이라 항목이 사라진다. 건수 비교로 삭제는 잡히지만,
    건수가 같은 채로 내용만 바뀌는 경우는 못 잡는다.
  - **첨부 기록** — 다섯 중 **가장 쉬운 그릇**이다. append-only 단일 파일이라 교훈과
    성질이 같아, 지금의 "`id:` 줄 수 vs 행 수" 판정이 그대로 통한다. 파일 형식은
    `---`로 나뉜 여러 문서라 세는 기준만 교훈과 다르다(9장 2절).
- 판정 방식을 그릇별로 정해 `BOWLS` 옆에 선언으로 두는 것을 권함(레지스트리 관례).

### 5단계 — 검색을 색인 방식으로 갈아끼우기
- `db.py:499` `search_bowl`의 **네** 분기(tasks / memo / **attachments** / profile)를
  색인 질의로 교체. 줄번호는 7장 끝의 "2026-08-08 재확인" 표를 볼 것(첨부 분기가
  끼면서 전부 밀렸다).
- `db.py:313` `_fts_query`를 그릇 공용으로 일반화(3자 미만 LIKE 폴백 포함 — 결정 4).
- **첨부 기록은 지금 `path`(파일 이름)까지 훑는다**(`db.py:616` 분기). 색인으로
  바꿔도 이 성질을 유지한다 — 첨부를 다시 찾을 때 사람이 기억하는 것은 대개 내용

## 9. 첨부 기록 그릇(attachments) — 다섯 번째 그릇 (2026-08-08 추가)

### 9.0 왜 이 장이 나중에 붙었나

이 문서를 쓴 2026-08-03에 그릇은 넷이었다. 8월 6~7일 `namu-file-upload-download`
작업으로 다섯 번째 그릇이 생겼고, **그 작업은 "첨부 기록을 검색 색인에 넣을지"를
자기 범위 밖으로 명시해 미뤄 두었다**(`config.py:245` 주석, `db.py:617-618` 주석,
그 작업의 `task.md` "범위 밖" 절). 이 문서가 그 미결을 넘겨받는다.

첨부 기록 그릇은 **올린 파일의 이력**만 담는다. 파일 몸통은 여기 없다 — 실물은
사용자 저장소의 `attach_file/` 폴더에 있고, 그 폴더는 각 PC에서 격리되어 안
내려온다. 그래서 이 파일이 "무슨 파일이 있고 왜 올렸나"에 답하는 유일한 자리다.

### 9.1 지금 읽는 방식 (2026-08-08 확인)

| 항목 | 값 |
|---|---|
| 원본 파일 | `~/.namu/memory/attachments.yaml` |
| 형식 | `---`로 나뉜 여러 문서 (append-only, `profile.yaml`과 같은 형식) |
| 로드 | `attachments.py:103` `load_all` — 통째로 읽어 파이썬 부분일치 |
| 검색 분기 | `db.py:616` (SQLite를 타지 않음) |
| 3층 헬퍼 `layers()` | **없다** — 만들어야 한다(6장 2단계) |
| 살아 있는 파일 계산 | `attachments.py:121` `current_files` |
| 한 파일의 이력 | `attachments.py:141` `history` |
| 그릇 선언 | `config.py:247` (`mutable=False`, `merge="union"`, `cached=False`) |
| 이 PC의 실제 규모 | 기록 15건 · 8,370바이트 (2026-08-08 측정) |

규모는 다섯 그릇 중 가장 작다(같은 시점 쪽지 36KB · 개인 사실 32KB). **성능이 아니라
통일성이 이 그릇을 넣는 이유**라는 점은 2장과 같다.

### 9.2 칸 구성 — 색인 표를 만들 때 그대로 쓸 것

`config.FIELDS`에서 이 그릇이 받는 칸(2026-08-08 확인). ★는 **필수**다.

| 칸 | 무엇 | 비고 |
|---|---|---|
| ★ `summary` | 이 파일이 무엇인가 한 줄 | 모든 그릇 공통 3층 |
| ★ `reason` | 왜 만들었고 왜 올렸나 | 〃 |
| ★ `body` | 그때 무슨 일이 있었나 | 〃 |
| ★ `path` | 저장소 안 경로 (`attach_file/<이름>`) | **이 그릇에만 있는 칸** |
| ★ `bytes` | 파일 크기(정수) | **이 그릇에만 있는 칸** · 9.3의 급소 |
| ★ `status` | `올림` / `새 판` / `지움` 셋 중 하나 | 닫힌 값 목록 |
| `topic` | 관련 작업 이름 — **저장될 때 칸 이름은 `task`** | 입력 이름과 저장 이름이 다르다 |
| `project` | 어느 프로젝트 | `tasks`와 이 그릇만 갖는 축 |
| `tags` | 꼬리표 목록 | |
| `supersedes` | 어느 기록을 대체하나 | `새 판`일 때 옛 기록을 가리킴 |
| `id` `timestamp` `machine` `via` | 모든 그릇 공통 | `id`는 ULID |

⚠ **`topic` → `task` 이름 바뀜에 주의한다.** 도구 인자는 `topic`인데 파일에 적히는
칸 이름은 `task`다(`attachments.py:86`). 색인 ingest는 **파일에 적힌 이름(`task`)**을
읽어야 한다.

### 9.3 급소 — 크기를 저장소에 물으면 격리가 무너진다

**이 그릇에서 색인을 만들 때 가장 중요한 제약이다.**

`bytes` 칸은 "있으면 좋은 정보"가 아니라 **없으면 목록 기능을 만들 수 없는 필수
칸**이다. 크기를 사용자 저장소에 물으면(`git ls-tree -l`) git이 크기를 알아내려고
**빠진 파일 몸통을 전부 내려받는다** — 2026-08-07 실측에서 파일 2,548개에 7분이
넘도록 끝나지 않아 중단했다. 이름만 묻는 `git ls-tree -r --name-only`는 즉시 끝난다.

**색인 작업에 주는 규칙:**

1. 색인 ingest의 입력원은 **`attachments.yaml` 하나뿐이다.** 저장소에 파일 목록이나
   크기를 물어 보완하지 않는다.
2. 색인이 낡았는지 판정할 때도 저장소를 건드리지 않는다. 판정 근거는 yaml 파일의
   기록 수뿐이다(6장 3단계).
3. 재색인이 이 규칙을 어기면 **"색인 다시 만들기" 한 번에 사용자의 첨부 파일 전체가
   그 PC로 내려온다.** 되돌릴 수 없다 — 한 번 받은 파일은 설정을 걸어도 안 사라진다.

근거: 정정 쪽지 `01KZD3653TX8VFB7RT47SRC0A1`(2026-08-07), `attachments.py:60-63` 주석.

### 9.4 색인으로 바꿔도 유지해야 할 성질

**① 파일 이름(`path`)도 검색 대상이다.**
지금 분기(`db.py:616`)는 `path`·`summary`·`reason`·`body`·`task`·`project`·`tags`를
한 덩어리로 이어 붙여 부분일치를 본다. 첨부를 다시 찾을 때 사람이 기억하는 것은
대개 내용 설명이 아니라 파일 이름이므로, 색인 텍스트에도 `path`를 반드시 넣는다.
(trigram 색인은 `보고서.pdf` 같은 이름 조각 찾기에 지금보다 오히려 낫다.)

**② 색인 행의 단위는 파일이 아니라 기록이다.**
같은 파일에 `올림` → `새 판` → `지움`이 여러 줄로 쌓인다. 최신 한 줄만 색인하면
"그 자료 어디 갔지?"에 답할 수 없게 된다 — 지운 파일의 기록과 그 이유가 검색에서
사라지기 때문이다. **모든 기록을 색인하고, "지금 살아 있는 파일"은 조회 결과에서
다시 계산한다**(`current_files`와 같은 계산: 경로별 마지막 기록을 보고 `지움`이면 뺀다).

**③ `project`·`task` 축이 이미 쓰인다.**
`search_bowl`은 `project` 축을 `tasks`와 `attachments`에만 허용한다(`db.py:542`).
색인 표에도 이 두 칸을 컬럼으로 두어 축 필터가 색인 안에서 끝나게 한다.

**④ 낱말 AND 검색은 이 그릇에도 그대로 적용된다**(7장 끝 참고). 지금은 통짜
부분일치라 `PDF 매뉴얼`처럼 띄어 쓰면 순서가 다를 때 0건이 된다.

### 9.5 이 그릇이 쉬운 점

- **mutable이 아니다.** 쪽지처럼 항목이 사라지지 않으므로, 교훈과 같은 "건수 비교"
  판정이 그대로 통한다. 다섯 그릇 중 낡음 판정이 가장 단순하다.
- **파일이 하나다.** 작업일지처럼 수십 개 파일을 훑을 필요가 없다.
- **작다.** 2026-08-08 기준 15건 8KB — 전체 재색인 비용이 사실상 0이다.
