# 검색 통일 — 네 그릇을 모두 SQLite 색인으로

**작업**: `fts5-memo-tasks-index` (namu-agent)
**결정일**: 2026-08-03 · **결정자**: 사용자 · **상태**: 설계 확정, 구현 미착수
**착수 지점**: 아래 6장 1단계

---

## 1. 한 줄 목적

지금은 그릇마다 조회 방식이 달라 교훈만 색인을 타고 나머지 셋은 매번 파일을 통째로 읽는다.
**네 그릇을 모두 SQLite 색인으로 통일해 조회 경로를 하나로 만든다.**

## 2. 왜 하는가 (확정된 근거)

사용자가 밝힌 판단 근거는 **성능이 아니라 통일성**이다 — "교훈만 색인처리 되었고 나머지는
각각의 파일을 끌고 다니며 통으로 조회한다. 전체를 색인해 SQLite로 검색하는 것이 통일성
있고 이후까지 효율적이다."

이 진단은 코드와 일치한다(2026-08-03 실측):

| 그릇 | 지금 읽는 방식 | 코드 |
|---|---|---|
| 교훈(learnings) | SQLite + FTS5(trigram) | `db.py:40` |
| 작업일지(tasks) | log.md 78개를 매 질의마다 열어 합침 | `db.py:552` → `task_resolve.journal` |
| 개인 사실(profile) | profile.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:606` |
| 쪽지(memo) | memo.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:572` |

## 3. 앞선 웹 설계문서에서 살린 것과 버린 것

원본: 쪽지 `01KZ3CEB0V3KYE7EH2322MGYFZ` ("FTS5(trigram) 검색 인덱스 설계 문서",
2026-08-03 17:39, 웹 세션 작성).

**살린 것 (처방)**
- SQLite FTS5 + `tokenize='trigram'`
- 색인은 "지워도 다시 만들 수 있는 사본"으로 취급, 원본은 파일 그대로
- 원본 갱신 시 색인 자동 동기화(트리거 또는 재색인)
- 증분 재색인(변경된 것만)

**버린 것 (전제 — 실측으로 반증됨)**

| 문서의 주장 | 실측 결과 |
|---|---|
| 쪽지는 검색에서 완전히 제외됨 | **거짓.** `namu_search(bowl='memo', query='프로토콜')`이 해당 쪽지를 반환 |
| 작업일지는 정확일치라 조사·어미로 누락 | **거짓.** `q in text.lower()` 부분일치라 조사가 붙어도 걸림 |
| 개인 사실은 검색 대상이 아님 | **거짓.** `db.py:606`이 처리, '출력' 질의로 3건 반환 |
| memo/tasks가 SQLite 표에 있다고 가정한 스키마 | **없음.** 실제 원본은 memo.yaml과 log.md 파일 |

문서가 제안한 trigram 색인은 **교훈에는 이미 적용돼 있다**(`db.py:40-44`).

> 이 문서가 왜 틀렸나: 코드를 볼 수 없는 웹 세션에서 작성됐고, `namu_search`의 도구
> 설명문이 "Search one of **THREE** memory bowls"라고 적고 쪽지를 목록에서 빼놓아
> (`mcp_server.py:592`) "쪽지는 검색 대상이 아니다"라고 믿을 수밖에 없었다.
> **5단계에서 이 설명문도 함께 고친다.**

## 4. 확정된 결정

1. **네 그릇 전부 SQLite 색인 대상**으로 한다.
2. **원본은 파일 그대로 둔다** — learnings.yaml / profile.yaml / memo.yaml / log.md.
   색인은 재생성 가능한 사본이며, 개발 원칙 2("원본이 곧 기억")를 그대로 유지한다.
   → 파일 읽기가 없어지는 게 아니라 **질의 시점에서 동기화 시점으로 옮겨간다.**
3. **쪽지는 자기 색인표를 갖는다** — 교훈 색인에 합치지 않는다.
   namu-56이 금지한 것은 "교훈 검색 색인에 섞이는 것"이지(`db.py:574` 주석 원문)
   색인을 갖는 것 자체가 아니다. 별도 표면 그 결정과 충돌하지 않는다.
4. **두 글자 우회는 필수** — 5장 참고. 안 넣으면 지금보다 나빠진다.
5. 검색 결과는 **지금과 같아야 한다** — 6단계에서 옛 경로와 대조 검증.

## 5. 두 글자 우회 (반드시 함께 들어갈 것)

trigram 색인은 글을 세 글자씩 겹쳐 잘라 저장한다. 검색어도 같은 방식으로 잘라 맞추므로
**두 글자 이하 검색어는 자를 조각이 없어 0건이 된다.** 실측:

```
색인 내용: "이 문서는 검색 인덱스 설계에 관한 것이다"
  '설계'   → 0건      '인덱스' → 1건
  '검색'   → 0건      '설계에' → 1건
```

우리말 기술용어는 두 글자가 가장 흔하다(설계·검색·기억·작업·문서·배포·캐시).
**지금은 파이썬 부분일치라 잘 찾히므로, 우회 없이 색인으로 바꾸면 검색 품질이 퇴행한다.**

**우회 방법**: 검색어가 3자 미만이면 색인을 건너뛰고 `LIKE` 전수 조회로 폴백한다.
교훈이 이미 이 구조다(`db.py:328` — `if len(q) >= 3:` 분기, else LIKE). 나머지 셋에
같은 규칙을 적용하면 되고, 새로 발명할 것은 없다.

## 6. 작업 단계 (다음 세션은 여기부터)

### 1단계 — 저장표와 색인 만들기
- `db.py:20` `_SCHEMA`에 tasks / memo / profile 표 + 각 `_fts` 가상표(trigram) + 트리거 추가.
- 쪽지 표는 **교훈 색인과 별도**(결정 3).
- 표 설계 주의: 작업일지의 단위는 "레코드"가 아니라 **log.md 한 줄**이다
  (`ts / project / task_slug / tag / machine / via / text / detail`).
  `task_resolve._parse_log_line`(`task_resolve.py:683`)이 이미 이 형태로 파싱한다.

### 2단계 — 원본 파일을 표에 채우기
- `db.py:153` `rebuild_from_yaml`이 교훈용 단일 구현이다. 그릇별 ingest로 일반화한다.
- 입력원: `task_resolve.journal`(`task_resolve.py:724`), `memo.load_all`(`memo.py:33`),
  `profile.active`(`profile.py:105`).
- 3층 텍스트는 각 그릇의 `layers()` 헬퍼를 쓴다(`memo.py:94`, `profile.py:83`) —
  옛 형식 항목도 같은 헬퍼가 돌려주므로 검색에서 빠지지 않는다.

### 3단계 — "색인이 낡았나" 판정을 그릇마다 정하기
- 지금 판정(`db.py:198` `cache_is_stale`)은 **교훈 전용**이다: ①스키마 컬럼 검사
  ②yaml의 `id:` 줄 수 vs db 행 수.
- 그대로는 안 통하는 이유:
  - **작업일지** — 원본이 파일 78개다. 한 파일의 줄 수 세기로는 부족하고,
    파일 목록 + 각 파일 크기·수정시각 또는 전체 줄 수 합계가 필요하다.
  - **쪽지** — 유일한 mutable 그릇이라 항목이 사라진다. 건수 비교로 삭제는 잡히지만,
    건수가 같은 채로 내용만 바뀌는 경우는 못 잡는다.
- 판정 방식을 그릇별로 정해 `BOWLS` 옆에 선언으로 두는 것을 권함(레지스트리 관례).

### 4단계 — 갱신 시점 배선
같은 판정을 부르는 곳이 이미 셋이다. 전부 그릇 전체를 보도록 넓힌다.

| 위치 | 파일·줄 |
|---|---|
| 세션 시작 훅 | `hooks/session_recall.py:43`, `hooks/session_inject.py:27` |
| MCP 서버 부팅 | `mcp_server.py:34` `_ensure_db` |
| 다른 PC에서 받아온 뒤(pull) | `memory_sync.py:76` |

### 5단계 — 검색을 색인 방식으로 갈아끼우기
- `db.py:499` `search_bowl`의 세 분기(tasks 552 / memo 572 / profile 606)를 색인 질의로 교체.
- `db.py:313` `_fts_query`를 그릇 공용으로 일반화(3자 미만 LIKE 폴백 포함 — 결정 4).
- **함께 고칠 것**: `mcp_server.py:592` 도구 설명문 "THREE bowls" → 네 그릇으로.
  쪽지가 목록에 없어서 이번 설계 오해가 생겼다.

### 6단계 — 검증과 배포
- **결과 동일성 대조**: 옛 경로와 새 경로에 같은 질의를 넣어 결과 집합을 비교한다.
  최소 포함 질의: 두 글자(`설계`, `검색`), 세 글자 이상(`인덱스`), 조사 결합

- `config.BOWLS`의 `cached` 플래그를 갱신하면 `test_bowls.py:73-76`이 함께 바뀐다.
- 색인 없음을 전제로 쓰인 테스트: `test_cache_stale.py`, `test_hook_stale_rebuild.py`,
  `test_db_bowl.py`, `test_memo.py`, `test_mcp_memo.py`, `test_memory_sync.py`.
- 문서 갱신: `CLAUDE.md`(쪽지 "SQLite 인덱싱 안 함" 서술, 그릇 레지스트리 절),

- 배포: 버전 bump는 `scripts/namu_bump.py`, 반영은 push → plugin update.

### 지금 실제로 못 찾는 검색 (색인과 별개로 5단계에서 함께 고칠 것)

낱말을 띄어 쓰면 **순서가 다를 때 0건**이 된다. 네 그릇 전부 같은 증상이다.

```
교훈     '설계 문서' 3건  /  '문서 설계' 0건
쪽지     'FTS5' 1건, '설계' 1건  /  'FTS5 설계' 0건   (같은 문서에 둘 다 있음)
작업일지 'FTS5 트리거' 0건                             (같은 줄에 둘 다 있음)
개인사실 '출력 규칙' 1건  /  '규칙 출력' 0건
```

원인: 교훈은 질의 전체를 구(phrase)로 던지고(`db.py:329`), 나머지 셋은 통짜 부분일치라
같은 결과가 된다. **낱말별로 나눠 모두 포함(AND)으로 바꾸면 해결된다.**
