## 1. 한 줄 목적

지금은 그릇마다 조회 방식이 달라 교훈만 색인을 타고 나머지 넷은 매번 파일을 통째로 읽는다.
**다섯 그릇을 모두 SQLite 색인으로 통일해 조회 경로를 하나로 만든다.**

## 2. 왜 하는가 (확정된 근거)

사용자가 밝힌 판단 근거는 **성능이 아니라 통일성**이다 — "교훈만 색인처리 되었고 나머지는
각각의 파일을 끌고 다니며 통으로 조회한다. 전체를 색인해 SQLite로 검색하는 것이 통일성
있고 이후까지 효율적이다."

이 진단은 코드와 일치한다(2026-08-03 실측):

| 그릇 | 지금 읽는 방식 | 코드 |
|---|---|---|
| 교훈(learnings) | SQLite + FTS5(trigram) | `db.py:40` |
| 작업일지(tasks) | log.md 78개를 매 질의마다 열어 합침 | `db.py:552` → `task_resolve.journal` |
| 개인 사실(profile) | profile.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:606` |
| 쪽지(memo) | memo.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:572` |
| 첨부 기록(attachments) | attachments.yaml 통째로 로드 후 파이썬 부분일치 | `db.py:616` (2026-08-08 추가, 9장) |

## 4. 확정된 결정

1. **다섯 그릇 전부 SQLite 색인 대상**으로 한다. (2026-08-08 개정 — 08-03 원문은 "네 그릇".
   첨부 기록 그릇을 넣을지는 `namu-file-upload-download`에서 "범위 밖"으로 미뤄 둔
   항목이었고, 이 문서가 그 결정을 넘겨받는다. 상세는 9장.)
2. **원본은 파일 그대로 둔다** — learnings.yaml / profile.yaml / memo.yaml / log.md /
   attachments.yaml.
   색인은 재생성 가능한 사본이며, 개발 원칙 2("원본이 곧 기억")를 그대로 유지한다.
   → 파일 읽기가 없어지는 게 아니라 **질의 시점에서 동기화 시점으로 옮겨간다.**
3. **쪽지는 자기 색인표를 갖는다** — 교훈 색인에 합치지 않는다.
   namu-56이 금지한 것은 "교훈 검색 색인에 섞이는 것"이지(`db.py:574` 주석 원문)
   색인을 갖는 것 자체가 아니다. 별도 표면 그 결정과 충돌하지 않는다.
4. **두 글자 우회는 필수** — 5장 참고. 안 넣으면 지금보다 나빠진다.
5. 검색 결과는 **지금과 같아야 한다** — 6단계에서 옛 경로와 대조 검증.

## 5. 두 글자 우회 (반드시 함께 들어갈 것)

trigram 색인은 글을 세 글자씩 겹쳐 잘라 저장한다. 검색어도 같은 방식으로 잘라 맞추므로
**두 글자 이하 검색어는 자를 조각이 없어 0건이 된다.** 실측:

```
색인 내용: "이 문서는 검색 인덱스 설계에 관한 것이다"
  '설계'   → 0건      '인덱스' → 1건
  '검색'   → 0건      '설계에' → 1건
```

우리말 기술용어는 두 글자가 가장 흔하다(설계·검색·기억·작업·문서·배포·캐시).
**지금은 파이썬 부분일치라 잘 찾히므로, 우회 없이 색인으로 바꾸면 검색 품질이 퇴행한다.**

**우회 방법**: 검색어가 3자 미만이면 색인을 건너뛰고 `LIKE` 전수 조회로 폴백한다.
교훈이 이미 이 구조다(`db.py:328` — `if len(q) >= 3:` 분기, else LIKE). 나머지 셋에
같은 규칙을 적용하면 되고, 새로 발명할 것은 없다.

## 6. 작업 단계 (다음 세션은 여기부터)

### 1단계 — 저장표와 색인 만들기
- `db.py:20` `_SCHEMA`에 tasks / memo / profile / **attachments** 표 + 각 `_fts`
  가상표(trigram) + 트리거 추가.
- 쪽지 표는 **교훈 색인과 별도**(결정 3).
- 첨부 기록 표의 단위는 **파일 하나가 아니라 기록 한 건**이다 — 같은 파일에
  올림 → 새 판 → 지움이 여러 줄로 쌓인다. 자세한 칸 구성은 9장 2절.
- 표 설계 주의: 작업일지의 단위는 "레코드"가 아니라 **log.md 한 줄**이다
  (`ts / project / task_slug / tag / machine / via / text / detail`).
  `task_resolve._parse_log_line`(`task_resolve.py:683`)이 이미 이 형태로 파싱한다.

### 2단계 — 원본 파일을 표에 채우기
- `db.py:153` `rebuild_from_yaml`이 교훈용 단일 구현이다. 그릇별 ingest로 일반화한다.
- 입력원: `task_resolve.journal`(`task_resolve.py:724`), `memo.load_all`(`memo.py:33`),
  `profile.active`(`profile.py:105`), **`attachments.load_all`(`attachments.py:103`)**.
- 3층 텍스트는 각 그릇의 `layers()` 헬퍼를 쓴다(`memo.py:94`, `profile.py:83`) —
  옛 형식 항목도 같은 헬퍼가 돌려주므로 검색에서 빠지지 않는다.
- ⚠ **첨부 기록에는 `layers()` 헬퍼가 아직 없다**(2026-08-08 확인 — `attachments.py`에
  있는 것은 `load_all`·`current_files`·`history` 셋뿐이다). 이 단계에서 만들어야 한다.
- ⚠ **첨부 기록의 입력원은 `attachments.yaml` 하나뿐이다.** 파일 목록이나 크기를
  사용자 저장소에 물어 보완하려 들면 안 된다 — 이유는 9장 3절(격리).

### 3단계 — "색인이 낡았나" 판정을 그릇마다 정하기
- 지금 판정(`db.py:198` `cache_is_stale`)은 **교훈 전용**이다: ①스키마 컬럼 검사
  ②yaml의 `id:` 줄 수 vs db 행 수.
- 그대로는 안 통하는 이유:
  - **작업일지** — 원본이 파일 78개다. 한 파일의 줄 수 세기로는 부족하고,
    파일 목록 + 각 파일 크기·수정시각 또는 전체 줄 수 합계가 필요하다.
  - **쪽지** — 유일한 mutable 그릇이라 항목이 사라진다. 건수 비교로 삭제는 잡히지만,
    건수가 같은 채로 내용만 바뀌는 경우는 못 잡는다.
  - **첨부 기록** — 다섯 중 **가장 쉬운 그릇**이다. append-only 단일 파일이라 교훈과
    성질이 같아, 지금의 "`id:` 줄 수 vs 행 수" 판정이 그대로 통한다. 파일 형식은
    `---`로 나뉜 여러 문서라 세는 기준만 교훈과 다르다(9장 2절).
- 판정 방식을 그릇별로 정해 `BOWLS` 옆에 선언으로 두는 것을 권함(레지스트리 관례).

### 5단계 — 검색을 색인 방식으로 갈아끼우기

  색인 질의로 교체. 줄번호는 7장 끝의 "2026-08-08 재확인" 표를 볼 것(첨부 분기가
  끼면서 전부 밀렸다).
- `db.py:313` `_fts_query`를 그릇 공용으로 일반화(3자 미만 LIKE 폴백 포함 — 결정 4).
- **첨부 기록은 지금 `path`(파일 이름)까지 훑는다**(`db.py:616` 분기). 색인으로

## 9. 첨부 기록 그릇(attachments) — 다섯 번째 그릇 (2026-08-08 추가)

### 9.0 왜 이 장이 나중에 붙었나

이 문서를 쓴 2026-08-03에 그릇은 넷이었다. 8월 6~7일 `namu-file-upload-download`
작업으로 다섯 번째 그릇이 생겼고, **그 작업은 "첨부 기록을 검색 색인에 넣을지"를
자기 범위 밖으로 명시해 미뤄 두었다**(`config.py:245` 주석, `db.py:617-618` 주석,
그 작업의 `task.md` "범위 밖" 절). 이 문서가 그 미결을 넘겨받는다.

첨부 기록 그릇은 **올린 파일의 이력**만 담는다. 파일 몸통은 여기 없다 — 실물은
사용자 저장소의 `attach_file/` 폴더에 있고, 그 폴더는 각 PC에서 격리되어 안
내려온다. 그래서 이 파일이 "무슨 파일이 있고 왜 올렸나"에 답하는 유일한 자리다.

### 9.1 지금 읽는 방식 (2026-08-08 확인)

| 항목 | 값 |
|---|---|
| 원본 파일 | `~/.namu/memory/attachments.yaml` |
| 형식 | `---`로 나뉜 여러 문서 (append-only, `profile.yaml`과 같은 형식) |
| 로드 | `attachments.py:103` `load_all` — 통째로 읽어 파이썬 부분일치 |
| 검색 분기 | `db.py:616` (SQLite를 타지 않음) |
| 3층 헬퍼 `layers()` | **없다** — 만들어야 한다(6장 2단계) |
| 살아 있는 파일 계산 | `attachments.py:121` `current_files` |
| 한 파일의 이력 | `attachments.py:141` `history` |
| 그릇 선언 | `config.py:247` (`mutable=False`, `merge="union"`, `cached=False`) |
| 이 PC의 실제 규모 | 기록 15건 · 8,370바이트 (2026-08-08 측정) |

규모는 다섯 그릇 중 가장 작다(같은 시점 쪽지 36KB · 개인 사실 32KB). **성능이 아니라
통일성이 이 그릇을 넣는 이유**라는 점은 2장과 같다.

### 9.2 칸 구성 — 색인 표를 만들 때 그대로 쓸 것

`config.FIELDS`에서 이 그릇이 받는 칸(2026-08-08 확인). ★는 **필수**다.

| 칸 | 무엇 | 비고 |
|---|---|---|
| ★ `summary` | 이 파일이 무엇인가 한 줄 | 모든 그릇 공통 3층 |
| ★ `reason` | 왜 만들었고 왜 올렸나 | 〃 |
| ★ `body` | 그때 무슨 일이 있었나 | 〃 |
| ★ `path` | 저장소 안 경로 (`attach_file/<이름>`) | **이 그릇에만 있는 칸** |
| ★ `bytes` | 파일 크기(정수) | **이 그릇에만 있는 칸** · 9.3의 급소 |
| ★ `status` | `올림` / `새 판` / `지움` 셋 중 하나 | 닫힌 값 목록 |
| `topic` | 관련 작업 이름 — **저장될 때 칸 이름은 `task`** | 입력 이름과 저장 이름이 다르다 |
| `project` | 어느 프로젝트 | `tasks`와 이 그릇만 갖는 축 |
| `tags` | 꼬리표 목록 | |
| `supersedes` | 어느 기록을 대체하나 | `새 판`일 때 옛 기록을 가리킴 |
| `id` `timestamp` `machine` `via` | 모든 그릇 공통 | `id`는 ULID |

⚠ **`topic` → `task` 이름 바뀜에 주의한다.** 도구 인자는 `topic`인데 파일에 적히는
칸 이름은 `task`다(`attachments.py:86`). 색인 ingest는 **파일에 적힌 이름(`task`)**을
읽어야 한다.

### 9.3 급소 — 크기를 저장소에 물으면 격리가 무너진다

**이 그릇에서 색인을 만들 때 가장 중요한 제약이다.**

`bytes` 칸은 "있으면 좋은 정보"가 아니라 **없으면 목록 기능을 만들 수 없는 필수
칸**이다. 크기를 사용자 저장소에 물으면(`git ls-tree -l`) git이 크기를 알아내려고
**빠진 파일 몸통을 전부 내려받는다** — 2026-08-07 실측에서 파일 2,548개에 7분이
넘도록 끝나지 않아 중단했다. 이름만 묻는 `git ls-tree -r --name-only`는 즉시 끝난다.

**색인 작업에 주는 규칙:**

1. 색인 ingest의 입력원은 **`attachments.yaml` 하나뿐이다.** 저장소에 파일 목록이나
   크기를 물어 보완하지 않는다.
2. 색인이 낡았는지 판정할 때도 저장소를 건드리지 않는다. 판정 근거는 yaml 파일의
   기록 수뿐이다(6장 3단계).
3. 재색인이 이 규칙을 어기면 **"색인 다시 만들기" 한 번에 사용자의 첨부 파일 전체가
   그 PC로 내려온다.** 되돌릴 수 없다 — 한 번 받은 파일은 설정을 걸어도 안 사라진다.

근거: 정정 쪽지 `01KZD3653TX8VFB7RT47SRC0A1`(2026-08-07), `attachments.py:60-63` 주석.

### 9.4 색인으로 바꿔도 유지해야 할 성질

**① 파일 이름(`path`)도 검색 대상이다.**
지금 분기(`db.py:616`)는 `path`·`summary`·`reason`·`body`·`task`·`project`·`tags`를
한 덩어리로 이어 붙여 부분일치를 본다. 첨부를 다시 찾을 때 사람이 기억하는 것은
대개 내용 설명이 아니라 파일 이름이므로, 색인 텍스트에도 `path`를 반드시 넣는다.
(trigram 색인은 `보고서.pdf` 같은 이름 조각 찾기에 지금보다 오히려 낫다.)

**② 색인 행의 단위는 파일이 아니라 기록이다.**
같은 파일에 `올림` → `새 판` → `지움`이 여러 줄로 쌓인다. 최신 한 줄만 색인하면
"그 자료 어디 갔지?"에 답할 수 없게 된다 — 지운 파일의 기록과 그 이유가 검색에서
사라지기 때문이다. **모든 기록을 색인하고, "지금 살아 있는 파일"은 조회 결과에서
다시 계산한다**(`current_files`와 같은 계산: 경로별 마지막 기록을 보고 `지움`이면 뺀다).

**③ `project`·`task` 축이 이미 쓰인다.**
`search_bowl`은 `project` 축을 `tasks`와 `attachments`에만 허용한다(`db.py:542`).
색인 표에도 이 두 칸을 컬럼으로 두어 축 필터가 색인 안에서 끝나게 한다.

**④ 낱말 AND 검색은 이 그릇에도 그대로 적용된다**(7장 끝 참고). 지금은 통짜
부분일치라 `PDF 매뉴얼`처럼 띄어 쓰면 순서가 다를 때 0건이 된다.

### 9.5 이 그릇이 쉬운 점

- **mutable이 아니다.** 쪽지처럼 항목이 사라지지 않으므로, 교훈과 같은 "건수 비교"
  판정이 그대로 통한다. 다섯 그릇 중 낡음 판정이 가장 단순하다.
- **파일이 하나다.** 작업일지처럼 수십 개 파일을 훑을 필요가 없다.
- **작다.** 2026-08-08 기준 15건 8KB — 전체 재색인 비용이 사실상 0이다.

### 9.6 6장 단계에 더해지는 일 (요약)

| 단계 | 첨부 기록 몫 |
|---|---|
| 1단계 | `attachments` 저장표 + trigram 가상표 + 트리거. 단위는 기록 한 건 |
| 2단계 | `attachments.py`에 `layers()` 신설 + ingest. 입력원은 yaml 하나뿐 |
| 3단계 | 낡음 판정 — 교훈과 같은 건수 비교(가장 쉬움) |
| 4단계 | 갱신 시점 3곳에 함께 태움 (별도 배선 없음) |
| 5단계 | `db.py:616` 분기를 색인 질의로 교체. `path` 포함 유지 |
| 6단계 | 파일 이름 질의로 옛 경로와 대조. `config.py:245`·`db.py:617-618` 주석 정정 |

## 10. 구현 결과 (2026-08-08)

### 10.1 무엇이 달라졌나

다섯 그릇이 모두 SQLite 색인을 탄다. 원본 파일은 하나도 안 건드렸고, 색인은 지워도
다시 만들어지는 사본이다(개발 원칙 2 유지).

| | 전 | 후 |
|---|---|---|
| 교훈 | `learnings` + `learnings_fts`(trigram) | 그대로 (질의 방식만 낱말 AND로) |
| 작업일지 | 질의마다 log.md 84개를 열어 합침 | `bowl_tasks` + `bowl_tasks_fts` |
| 개인 사실 | yaml 통째 로드 후 파이썬 부분일치 | `bowl_profile` + `bowl_profile_fts` |
| 쪽지 | 〃 | `bowl_memo` + `bowl_memo_fts` (교훈 색인과 **별도 표**) |
| 첨부 기록 | 〃 | `bowl_attachments` + `bowl_attachments_fts` |

넷은 표 모양이 같다 — `id / timestamp / machine / via / project / task / text / doc`.

- `doc` = **원본 기록 dict를 JSON으로 통째 담는다.** 검색 결과가 옛 경로와 글자
  하나까지 같아야 하는데(4장 결정 5), 칸을 골라 옮기면 그릇에 칸이 하나 늘 때마다
  색인이 조용히 그 칸을 빠뜨린다 — 첨부 기록 그릇이 실제로 그렇게 나중에 늘었다.
- `text` = 옛 파이썬 필터가 질의마다 만들던 건초더미를 색인 시점에 한 번 만든 것.
- 축 칸(machine/via/project/task/timestamp)만 따로 뺐다 — 이건 SQL이 걸러야 이득이 난다.

행은 **화면에 나갈 순서 그대로** 담고 질의는 언제나 `ORDER BY rowid`다. 정렬을 질의
쪽에 두면 동점 처리가 미묘하게 달라져 "대부분 같은데 가끔 다른" 회귀가 생기는데,
그건 발견이 가장 늦는 종류의 결함이다.

### 10.2 설계에서 달라진 것 (둘)

**① 낡음 판정을 그릇별로 나누지 않고 하나로 통일했다.**
6장 3단계는 그릇별 판정을 권했고 9.6은 첨부 기록에 "기록 수 비교"를 적었다. 구현에서는
**원본 파일들의 (경로·크기·수정시각)을 모아 해시한 서명 하나**로 다섯 경우를 모두 덮었다
(`db._bowl_signature`, 교훈만 종전 판정 유지). 근거: ①작업일지는 어차피 파일 목록+크기·
시각이 필요하고 ②쪽지는 mutable이라 건수 비교로는 "건수가 같은 채 내용만 바뀐" 경우를
못 잡는다. 판정이 그릇마다 갈라지면 이 작업이 없애려는 결함(그릇마다 다른 경로)이
판정 쪽에서 그대로 되살아난다. 서명에는 표 스키마 판(`_INDEX_SCHEMA_VERSION`)도 섞어,
표 모양을 바꾸면 원본이 그대로여도 기존 설치본이 자동으로 다시 만든다.
9.3의 금지선은 그대로 지킨다 — 서명은 `attachments.yaml` 한 장만 stat하고 사용자
저장소(`attach_file/`)는 건드리지 않는다.

**② 색인 갱신을 세션 시작 3곳에만 걸지 않고 검색 진입점에서도 확인한다.**
4단계 배선(세션 시작 훅 2곳·MCP 부팅·pull 직후)은 그대로 넣되, `search_bowl`이 질의
직전에 한 번 더 본다. 안 그러면 **방금 남긴 기록이 다음 검색에 안 잡히는** 구멍이
생기는데, 옛 경로는 질의마다 파일을 읽어 그 구멍이 없었다. 판정 비용은 stat 몇 번이다
(작업일지 2.6ms, 나머지 0.4ms).

### 10.3 실측 (2026-08-08, 실제 데이터: 교훈 204건·작업일지 625줄/84파일·쪽지 6·개인 사실 12·첨부 15)

| 검색 한 번 (낡음 판정 포함) | 옛 경로 | 새 경로 |
|---|---|---|
| 작업일지 | 16.3ms | **3.7ms** |
| 쪽지 | 20.8ms | **1.2ms** |
| 개인 사실 | 28.3ms | **1.1ms** |
| 첨부 기록 | 17.6ms | **1.0ms** |

색인 다시 만들기(그 그릇의 원본이 바뀌었을 때만): 작업일지 380ms · 나머지 60~90ms.
다섯 그릇 전체 최초 생성 1.35초.

### 10.4 결과 동일성 대조 (6단계)

옛 코드(`git show HEAD:namu-plugin/db.py`)와 새 코드에 같은 질의를 넣어 대조했다.
질의 186가지 — 다섯 그릇 × (검색어 없음·두 글자·세 글자 이상·조사 결합·영문·한 글자)
× (limit 있음/없음) + 축 필터(machine·via·since·until·project·task) 조합.

- **단일 낱말·축 질의: 186가지 전부 동일** (결과 순서까지).
- **반환 항목의 내용: 네 그릇 전부 글자 그대로 동일** — 작업일지 625건, 쪽지 6건,
  개인 사실 12건, 첨부 15건을 JSON으로 직렬화해 비교.
- **여러 낱말 질의는 의도적으로 달라진다**(7장 끝 결함 수정). 30가지 중 19가지에서
  결과가 늘었고 줄어든 것은 없다. 예: 교훈 `문서 설계` 0건 → 26건, 작업일지
  `FTS5 설계` 2건 → 5건, 개인 사실 `규칙 출력` 0건 → 3건.

기존 테스트 665개 전부 통과, 새 테스트 24개 추가(`test_bowl_index.py`).

### 10.5 이 작업이 뒤집은 옛 결정

| 옛 결정 | 어디에 적혀 있었나 | 지금 |
|---|---|---|
| 작업일지는 색인 유지 비용이 이득보다 크다 | `db.py` `search_bowl` 독스트링 | 색인함 — 근거는 성능이 아니라 통일성 |
| 쪽지는 SQLite 인덱싱 안 함 | `CLAUDE.md`, `config.py` MEMO 주석 | **자기 표**를 가짐(교훈 색인과 분리는 유지) |
| 개인 사실은 캐시 이득보다 유지 비용이 큼 | `docs/mcp_memory_design.md` | 검색 경로만 색인. `recall`의 통째 로딩은 종전대로 |
| 첨부 기록의 색인 여부는 범위 밖 | `config.py:245` 주석, `db.py` 첨부 분기 주석 | 이 작업이 넘겨받아 색인함 |

### 10.6 뒤늦게 드러난 갈래 — 클라우드 작업일지 (v0.1.61에서 해소)

v0.1.60 배포 직후 확인된 것: **낱말 AND 개선이 클라우드의 작업일지 검색에만 안 들어갔다.**

원인은 색인이 아니라 **베낀 사본**이다. 클라우드 라우팅은 다섯 그릇 중 넷을 코어
(`db.search_bowl`·`db.search`)에 맡기지만, 작업일지만 회원별 폴더를 훑어야 해서
`_task_journal_for_user`로 함수를 복사해 왔고 그때 **거르는 규칙까지 함께 복사됐다**
(`routing_server.py` 549~566줄: `q in text.lower() or ...`). 코어를 고쳐도 그 사본은
안 따라온다. 정작 같은 파일의 다른 그릇 분기에는 "거르는 규칙을 여기 베끼지 않고
코어에 맡긴다 — 베끼면 그 순간 두 서버가 또 갈라진다"고 적혀 있었다.

**해소**: 코어가 낱말 규칙을 공개 함수로 내준다 — `db.query_tokens`(낱말 쪼개기)와
`db.matches_all_tokens(query, *fields)`(전부 포함 판정). 색인을 타는 경로와 같은 뜻을
파이썬 쪽에 둔 것이라, 색인을 못 쓰는 조회가 이걸 부르면 두 경로가 갈라지지 않는다.
클라우드의 작업일지 분기는 사본을 지우고 이 함수를 부른다.

교훈의 일반형: **조회 경로를 통일한다는 말은 색인을 통일한다는 뜻이 아니다.**
색인을 못 타는 경로가 하나라도 남으면 규칙은 거기로 새어 나가 복사되고, 개선은
복사본에 닿지 않는다. 통일해야 하는 것은 저장소가 아니라 **판정 규칙**이며, 그것을
부를 수 있게 열어 두는 것이 베끼기를 막는 유일한 방법이다.

## 11. 작업 설명서(task.md)를 작업일지 검색에 넣기 (2026-08-08 추가)

### 11.1 왜 뒤늦게 붙었나

색인 통일을 배포까지 끝낸 뒤 "모든 기억파일이 색인에 걸린 거냐"는 물음에 파일을
세어 보니 **`task.md` 84장이 통째로 빠져 있었다.** 검색은 `log.md`만 봤다. 전에도
그랬으므로 이 작업의 회귀는 아니지만, 실측으로 다음이 확인됐다.

- 84개 작업 **전부** `task.md`에만 있는 줄을 갖고 있다(모든 `log.md`를 한 덩어리로
  만들어 대조).
- 실제 질의: 작업일지 `'네이티브 서브에이전트 대칭'` 0건, `'안내서 4종 검토'` 0건 —
  둘 다 어느 작업의 제목이다.

사용자가 넣기로 결정했다(2026-08-08).

### 11.2 정한 것 둘 (사용자 결정)

| | 결정 | 왜 |
|---|---|---|
| 담는 단위 | **문서 한 장 = 결과 한 건** | 설명서는 제목·목적·완료조건이 한 덩어리로 하나의 답을 이룬다. 줄로 쪼개면 `- [x] 안내서 4종 검토` 한 줄만 걸려 어느 작업의 무엇인지 알 수 없고, 검색 대상 줄이 625줄 → 2,091줄로 불어나 일지 쪽 결과까지 묻힌다 |
| 반환 모양 | **같은 그릇·같은 칸 구성, `tag`만 `설명서`** | 이 결과를 받는 곳이 셋(플러그인·웹·클라우드)이다. 새 모양을 만들면 셋을 다 고쳐야 하고, 안 고친 곳에서는 설명서가 조용히 사라진다. 칸이 같으면 안 고친 곳도 그대로 뜬다 |

### 11.3 시각을 어디서 얻나

`task.md`에는 시각도 기기도 없다. 머리말 `📅 생성 2026-07-31 [hp] · 🔗 관련: __`에서
뽑으며, 로그 줄과 **같은 폭**(`YYYY-MM-DD HH:MM:SS`)으로 맞춘다 — 폭이 다르면
한 목록에서 사전순 비교가 어긋난다(`2026-07-31` < `2026-07-31 00:00:00`).

실물 84장 중 **3장**(namu-16·39·40)에는 그 줄이 없다. 이 형식이 굳기 전에
만들어졌고 `task.md`는 불변이라 원본을 고칠 수 없다. 그래서 **그 작업 `log.md`의
가장 이른 줄**로 대신한다 — 생성 시각의 가장 정확한 근사이며, 셋 다 그 줄에 시각이
있는 것을 확인했다. 시각이 비면 정렬에서 맨 뒤로 밀리고 since/until 필터에서 통째로
빠지므로 폴백이 없으면 그 3장은 사실상 안 잡힌다.

머리말 5줄까지만 본다 — 본문의 `색인을 생성 2026-01-01에 만들기로 했다` 같은 서술을
생성 시각으로 오인하지 않기 위해서다.

### 11.4 고친 자리

| 파일 | 무엇 |
|---|---|
| `task_resolve.py` | `parse_task_doc(path, project)`·`task_docs()`·`TASK_DOC_TAG` 신설. `_title_from_text`를 갈라내 제목 규칙이 두 벌이 되지 않게 했다 |
| `db.py` `_bowl_source_files` | `*/*/task.md`를 목록에 더한다. **판정에서 빼면 설명서만 고친 경우(완료조건 체크 등) 서명이 그대로라 색인이 영영 안 따라온다** |
| `db.py` `_bowl_rows` | 일지 줄 + 설명서를 합쳐 journal과 **같은 키**로 다시 세운다. 키가 같고 파이썬 정렬이 안정 정렬이라 일지 줄끼리의 상대 순서는 합치기 전과 글자 그대로 같다 |
| `mcp_server.py` / 클라우드 `routing_server.py` | 도구 설명문에 설명서 항목 추가 |
| 클라우드 `_task_journal_for_user` | 같은 몫. 폴더를 정하는 부분만 회원별이고, **파싱은 코어 `parse_task_doc`을 부른다** — 10.6이 적은 사고(규칙을 베껴 와 두 서버가 갈라진 일)를 되풀이하지 않기 위해서다 |

### 11.5 `journal()`에 합치지 않은 이유

`journal()`은 검색만 쓰는 게 아니라 **브리핑의 "최근 활동"과 마무리 검사
(`closing_guard`)도 함께 쓴다.** 설명서를 거기 섞으면 오늘 아무 일도 없던 작업
84개가 활동 목록에 나타나 "어제 무슨 일이 있었나"의 답이 망가진다. 설명서가 필요한
곳은 검색뿐이라 합류 지점도 색인 한 곳(`db._bowl_rows`)뿐이다.

### 11.6 낡은 전제가 된 시험 6개

기존 시험 여섯 개가 실패했는데 전부 **건수 계산**이었다 — 시험 헬퍼가 `task.md`를
함께 만들고 있어서 작업일지 그릇 조회가 1건이 아니라 2건이 됐다. 결함이 아니라
결정한 동작이므로, 확인하려던 것(어느 방이 걸렸나 / 일지 줄이 반환되나)을 건수가
아닌 축으로 다시 적었다. 코어 703개·클라우드 502개 전부 통과.
