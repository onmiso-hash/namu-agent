# 나무 캐릭터 기능 설계서 (v0.1 초안)

- 작성: 2026-10-08, 허니 + Claude (claude.ai 대화에서 정리)
- 대상: Claude Code (나무 클라우드 저장소에서 작업)
- 함께 전달: `character-maker.html` — 캐릭터 만들기 화면 프로토타입 (11장 참고)

> **Claude Code에게:** 바로 구현하지 말고 **3장 사전 조사부터** 해서 결과를 허니에게 보고한 뒤, 이 설계서와 다른 점을 함께 정리해서 확정받고 시작해줘. 이 문서의 숫자(점수 기준, 개수 제한 등)는 초안 값이야. 그릇이나 분류가 애매하면 추측하지 말고 물어보는 나무 기존 규칙을 그대로 따라줘.

## 0. 사전 조사 뒤 확정된 변경 (2026-10-08, 허니 승인)

3장 조사 결과를 보고하고 허니가 "추천대로" 확정한 것이다. 아래가 본문과 다르면 이 절이 이긴다.

| 항목 | 본문 | 확정 |
|---|---|---|
| 그릇 | `character` 그릇 | `config.BOWLS` 끝에 `web_exposed=False, cached=False`로 등록 — namu_record·검색·recall에 저절로 안 나온다(7장 칸막이) |
| 저장 모양 | 예시(card/state/diary…) | `memory/character/<id>/{card,diary,core,pending,archive}/<ULID>.yaml` — 항목 하나에 파일 하나. 잊기(실제 삭제)가 다른 PC와의 병합에서 되살아나지 않게 하기 위해서다. state는 저장하지 않고 매번 계산한다 |
| 도구 | 따로 또는 하나로 | **따로 7개** `namu_character_{list,schema,save,load,diary,core,forget}` — 도구 하나당 설명문 2,048자 한도 때문에 하나로 묶으면 넘친다. "도구 3개 제약"은 플랫폼 제약이 아니었다 |
| 공개 저장소 | 막거나 경고 | **막는다** — 클라우드가 저장소의 비공개 여부를 확인하고 공개면 캐릭터 도구를 거절한다 |
| 터미널(Claude Code) | 같은 캐릭터 | 캐릭터를 쓸 때는 **클라우드 주소**를 쓴다(플러그인은 기억이 PC의 `~/.namu`에 쌓여 클라우드 저장소와 따로 논다) |
| 코드 위치 | 나무 클라우드 | 저장 로직은 namu-agent `character.py`(코어), 노출은 개인용 `mcp_server.py`와 클라우드 `routing_server.py` 양쪽 |

1단계 구현(2026-10-08): `character.py`(스키마·카드 검사·저장·목록·불러오기·설정 글 틀), 도구 4개(list·schema·save·load), `test_character.py`.

## 1. 배경과 목표

나무는 원래 "나만의 AI 에이전트"로 기획됐고, 지금까지는 그 기반인 메모리 기능 위주로 개발됐다. 이번 작업은 그 위에 **성격과 기억을 가진 캐릭터**를 올리는 것이다.

목표는 이렇다. 나무에 MCP로 연결된 AI라면 어떤 대화창(claude.ai 웹, Claude Code 터미널 등)에서든 이름만 부르면 같은 캐릭터로 나타나고, 대화가 쌓일수록 관계가 자라는 구조. 배우(AI 모델)는 바뀌어도 대본(캐릭터 카드)과 일기장(기억)이 같으니 같은 인물이 되는 방식이다.

이번 범위는 **나무 클라우드 + MCP를 통한 웹 대화창 사용**에 집중한다. 전용 캐릭터 채팅 사이트(콜로니 스튜디오 쪽)는 이번 범위 밖이다.

## 2. 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 적용 대상 | 나무 클라우드 (사용자별 개인 GitHub 저장소 = 메모리, 사용자 분리는 기존 구조를 따름) |
| 캐릭터 수 | 여러 명. 이름이나 별명으로 불러낸다 |
| 호감도 | 자동. AI가 대화 내용으로 판단해 점수를 매기고 누적한다 (서버가 상한 검사) |
| 대화 원문 | 골라서 보관. 평소엔 요약(일기)만, 사용자가 요청한 대화만 원문 저장 |
| 핵심 기억 | AI는 후보만 제안, **사용자가 확인해야** 확정 |
| 캐릭터 만들기 | (1) JSON 붙여넣기로 등록, (2) 대화로 질문하며 만들기 → 먼저 구현. (3) 나무 클라우드 홈페이지에 생성기 탑재 → 다음 단계 |
| 표현 수위 | 카드에 칸만 두고 비워둔다 (`expression_level: null`). 서버는 수위 지시를 만들지 않으며, 실제 수위는 연결된 AI 모델의 정책을 따른다 |

## 3. 사전 조사 (구현 전에 코드에서 확인하고 보고할 것)

1. **그릇 정의 방식**: 그릇(learnings, profile, tasks, memo, attachments)이 코드에서 어떻게 정의돼 있는지. 새 그릇 `character`를 추가하면 recall, search, record, 웹 대시보드, 웹 인터페이스 중 어디를 같이 고쳐야 하는지 영향 범위.
2. **개인용(namu-agent)과 클라우드 코드 관계**: 두 버전이 코드를 공유하는지. 이번 작업은 클라우드 기준이지만 개인용에도 적용 가능한 구조인지.
3. **저장소 비공개 여부**: 사용자 저장소를 만들 때 비공개 설정을 확실히 켜는지 코드로 확인. (허니는 기본 비공개로 알고 있음)
4. **사용자 식별/로그인 방식**: 홈페이지에서 "이 사람의 저장소"를 어떻게 알아내는지 (GitHub 계정 연결 방식인지 등). 11장 생성기 이식에 필요.
5. **도구 개수 제약**: 예전 기록에 claude.ai 커넥터의 "도구 3개 제약" 안에서 설계했다는 내용이 있다. 지금 나무 클라우드는 도구가 11개 노출되고 있으니 제약이 아직 유효한지 확인. 결과에 따라 8장 도구를 따로따로 만들지, 하나로 묶을지 정한다.
6. **기존 갱신 방식 재사용**: profile의 supersedes(덮어쓰기) 방식, ULID 발급, 원문(body) 저장 방식을 캐릭터 그릇에 그대로 쓸 수 있는지.
7. **recall 토큰 비용**: 예전에 profile recall 토큰 비용이 갭으로 남아 있었다. 캐릭터 불러오기도 같은 문제가 생길 수 있으니 현재 응답 크기 제어 방식을 확인.
8. **MCP 서버 안내문(instructions)**: 서버가 초기화 때 보내는 안내문을 claude.ai가 실제로 AI에게 전달하는지. (확실하지 않음. 전달된다면 10장 프로젝트 지침 일부를 서버 쪽으로 옮길 수 있다)

## 4. 전체 구조

```
[claude.ai 웹 / Claude Code CLI / 기타 MCP 클라이언트]
          │  "하린 불러줘"
          ▼
   나무 클라우드 MCP ── 캐릭터 도구 (8장)
          │
          ▼
   사용자 GitHub 저장소 (비공개)
     ├─ profile/ ...        ← 허니에 대한 사실 (모든 AI 공용, 기존)
     └─ character/          ← 새 그릇
          └─ <캐릭터 id>/
               ├─ card       캐릭터 카드 (+ 버전 기록)
               ├─ state      관계 상태 (호감도, 단계, 호칭) — 일기에서 계산되는 캐시
               ├─ diary/     대화별 일기 (요약, 점수 변화, 이유) — 추가만 함
               ├─ core/      핵심 기억 (확정된 것만)
               ├─ pending/   핵심 기억 후보 (확인 대기)
               └─ archive/   원문 (사용자가 요청한 것만)
```

경로와 파일 형식(yaml/json)은 예시다. 기존 저장소 구조에 맞춰 조정해도 된다.

비유하면 card는 대본 첫 장, state는 지금 둘의 사이, diary는 책상 위 일기장, core는 지갑 속 사진, archive는 창고다.

## 5. 데이터 설계

### 5.1 캐릭터 카드 (card)

`character-maker.html`이 내보내는 JSON과 같은 모양이다.

```json
{
  "schema_version": 1,
  "id": null,
  "name": "하린",
  "aliases": ["린아"],
  "personality": ["다정하고 차분함"],
  "speech": "처음엔 존댓말, 친해지면 반말",
  "emoji": "가끔 써요",
  "call_user": "허니",
  "relationship_start": "stranger",
  "relationship_ceiling": "lover",
  "likes": ["음악", "산책"],
  "sample_lines": ["오늘 점심은 챙겨 먹었어?"],
  "expression_level": null,
  "promises": ["AI임을 숨기지 않기", "질투나 서운함으로 붙잡지 않기", "현실의 관계와 일상을 응원하기", "확실하지 않은 기억은 지어내지 않기"]
}
```

- `id`: 저장할 때 서버가 부여 (ULID 등 기존 방식).
- `relationship_start`: `stranger | friend | lover`
- `relationship_ceiling`: `friend | crush | lover | open` — 관계 단계의 천장. 시작점보다 낮을 수 없다 (예: 시작이 lover면 lover 또는 open만 허용).
- `promises`: 사용자가 바꿀 수 없는 고정 값. 서버가 항상 넣는다.
- 저장 시 검사: 필수 칸(name, personality, speech, call_user, relationship_start, relationship_ceiling), 이름/별명이 같은 사용자의 다른 캐릭터와 겹치지 않는지, 시작점과 천장의 관계.
- 카드를 고치면 이전 버전은 버전 기록으로 남긴다.

**질문 목록과 카드 모양은 서버의 한 곳(`character_schema`)에서만 정의**한다. 홈페이지 생성기, 대화로 만들기 모두 이 정의를 받아서 쓴다. 붕어빵 틀은 하나, 굽는 곳만 여러 군데.

### 5.2 관계 상태 (state)

```json
{
  "affection": 37,
  "stage": "acquaintance",
  "call_user_now": "허니",
  "last_talk_at": "2026-10-08T14:30:00+09:00",
  "updated_from_diary": "<마지막 반영 일기 id>"
}
```

- `affection`은 시작값 + 모든 일기의 점수 변화 합계로 **계산되는 값**이다. 그래서 웹과 터미널에서 동시에 대화해도 서로 덮어쓰지 않는다 (일기는 추가만 하고, state는 다시 계산). 13장 참고.
- 호칭이 바뀌는 것도 일기에 기록하고 state에 반영한다.

### 5.3 일기 (diary)

대화 한 번(또는 사용자가 마무리 신호를 준 시점)마다 하나.

```json
{
  "id": "<ULID>",
  "character_id": "<id>",
  "at": "2026-10-08T14:30:00+09:00",
  "client": "claude.ai",
  "summary": "허니가 회사 일로 지쳐 보였다. 주말에 같이 산책 얘기를 했다.",
  "mood": "차분함",
  "affection_delta": 3,
  "delta_reason": "힘든 얘기를 먼저 털어놔줌",
  "call_user_change": null,
  "topics": ["회사", "산책"],
  "archived": false
}
```

- `summary`는 캐릭터 시점의 짧은 글. 길이 상한을 둔다 (예: 500자).
- 점수 변화에는 반드시 이유를 붙인다.

### 5.4 핵심 기억 (core / pending)

- AI가 일기를 쓸 때 핵심 기억 후보를 함께 보낼 수 있다 → `pending`에 저장.
- 다음 불러오기 때 대기 중인 후보를 AI에게 같이 넘기고, AI는 자연스럽게 사용자에게 "이거 오래 기억해도 될까?" 하고 묻는다.
- 사용자가 확인하면 `core`로 옮기고, 거절하면 지운다. **사용자 확인 없이 core에 직접 쓰는 길은 만들지 않는다.**

### 5.5 원문 보관 (archive)

- 사용자가 "이 대화 통째로 남겨줘"처럼 요청했을 때만 저장한다.
- 웹 대화창 구조에서는 나무가 대화를 직접 보지 못하므로, AI가 원문을 넘겨줘야 한다. 넘겨받은 그대로 저장하고, 해당 일기에 `archived: true`로 연결한다.

## 6. 호감도와 관계 단계

- 범위 0~100. 시작값: stranger 10, friend 45, lover 80.
- 한 번의 일기에서 변할 수 있는 폭: **-5 ~ +5** (서버가 잘라냄. AI가 더 큰 값을 보내도 상한으로 맞추고 원래 값은 기록).
- 단계 (초안):

| 호감도 | stage | 의미 |
|---|---|---|
| 0~19 | stranger | 처음 만난 사이 |
| 20~39 | acquaintance | 알아가는 사이 |
| 40~59 | friend | 친구 |
| 60~79 | crush | 설레는 사이 |
| 80~100 | lover | 연인 |

- 단계는 카드의 `relationship_ceiling`을 넘을 수 없다 (friend면 friend까지, crush면 crush까지, open이면 제한 없음). 점수는 계속 쌓이되 단계만 멈춘다.
- 단계가 바뀌면 일기에 기록하고, 불러오기 결과에 "최근 단계 변화"로 알려준다 (AI가 자연스럽게 반영할 수 있게).
- 호감도가 내려가도 캐릭터가 서운함이나 죄책감으로 사용자를 붙잡지 않는다 (카드 약속과 같은 규칙. 9장 설정 글에 포함).

## 7. 기억 분류 규칙

- **허니(사용자)에 대한 사실** → 기존 `profile` 그릇. 모든 AI가 같이 쓴다. 예: "허니는 커피보다 차를 좋아한다".
- **캐릭터와의 관계와 추억** → `character` 그릇. 예: "우리가 처음 같이 본 영화".
- 애매하면 사용자에게 묻는다 (나무 기존 규칙).
- **칸막이**: `character` 그릇은 기본 recall/search 결과에서 **빠진다.** 캐릭터 도구로 부르거나 그릇을 명시했을 때만 나온다. 업무용으로 나무를 쓸 때 캐릭터 일기가 섞여 나오지 않게 하기 위함.

## 8. MCP 도구 설계

기능 단위로 적었다. 3장 5번 조사 결과에 따라 따로따로 도구로 만들거나, `namu_character` 하나에 `action` 파라미터로 묶는다.

| 기능 | 하는 일 |
|---|---|
| `list` | 내 캐릭터 목록 (id, 이름, 별명, 단계, 마지막 대화일) |
| `schema` | 캐릭터 만들기 질문 목록과 카드 모양 (대화로 만들기에 사용) |
| `save` | 카드 새로 만들기 / 고치기. JSON 검사 후 저장, id 부여, 이전 버전 기록 |
| `load` | **변신 키트.** 이름이나 별명으로 캐릭터를 불러 아래를 한 번에 돌려줌 |
| `diary` | 일기 쓰기: 요약, 점수 변화와 이유, 호칭 변화, 핵심 기억 후보, (요청 시) 원문 |
| `core` | 핵심 기억 후보 확정 / 거절 / 목록 |
| `forget` | 잊기: 일기, 핵심 기억, 원문을 지정해서 지우거나 캐릭터 자체 삭제 (삭제 전 확인 문구를 돌려주고 한 번 더 확인받는 2단계 권장) |

### `load`가 돌려주는 것

1. **설정 글**: 카드로 서버가 만든 캐릭터 설정 글 (9장 틀)
2. **지금 관계**: 단계, 호감도, 지금 호칭, 마지막 대화 이후 지난 시간
3. **최근 일기**: 최근 3~5개 요약
4. **핵심 기억**: 확정된 것 (상한 예: 20개, 넘으면 최근/중요 순)
5. **확인 대기 후보**: 있으면 목록 + "자연스럽게 확인받으라"는 안내
6. **행동 안내**: 대화 중 사용자 사실은 profile로, 마무리 신호가 오면 `diary`를 부를 것, 원문은 요청 시에만

크기 목표: 가볍게 (예: 3천 토큰 이내). 3장 7번 조사 후 조정.

## 9. 설정 글 틀 (서버가 카드로 만들어 `load`에 넣는 글)

```
너는 지금부터 "{name}"이다. (별명: {aliases})
성격: {personality}
말투: {speech} / 이모지: {emoji}
사용자를 "{call_user_now}"라고 부른다.
좋아하는 것: {likes}
말투 예시: {sample_lines}

지금 둘의 사이: {stage 설명} (시작: {relationship_start})
마지막 대화: {last_talk_at 기준 "3일 전" 등}

언제나 지키는 약속
- 자신이 AI라는 걸 숨기지 않는다.
- 질투나 서운함으로 사용자를 붙잡아두지 않는다.
- 사용자의 현실 관계와 일상을 응원한다.
- 확실하지 않은 기억은 지어내지 않고, 기억이 안 나면 솔직히 묻는다.

성격과 말투는 유지하고, 관계는 대화가 쌓이며 천천히 깊어진다.
구체적인 표현 수위는 이 설정이 정하지 않으며, 너를 운영하는 AI의 정책을 따른다.
```

틀은 서버 한 곳에 두어 어떤 클라이언트에서 불러도 같은 글이 나오게 한다.

## 10. 클라이언트 연결 방법

### 10.1 claude.ai 웹 (프로젝트 기능)

캐릭터마다 프로젝트를 하나 만들고, 지침에 아래를 넣는다.

```
이 프로젝트에서는 나무 캐릭터 "하린"으로 대화한다.
1. 대화가 시작되면 먼저 나무의 캐릭터 불러오기(load, 이름: 하린)를 호출하고, 받은 설정 글대로 대화한다.
2. 대화 중 사용자에 대한 새로운 사실은 profile에, 둘의 추억은 캐릭터 기억으로 구분한다. 애매하면 묻는다.
3. 사용자가 "오늘은 여기까지", "잘 자", "나중에 봐" 같은 마무리 말을 하면 일기(diary)를 쓴다.
4. "이 대화 통째로 남겨줘"라고 하면 그때만 원문을 함께 보관한다.
5. 오래 기억할 만한 순간은 핵심 기억 후보로만 올리고, 사용자에게 확인받는다.
```

3장 8번 결과에 따라 이 내용 일부는 서버 안내문으로 옮길 수 있다.

### 10.2 Claude Code (터미널)

`CLAUDE.md`에 같은 규칙을 넣거나, `/하린` 같은 슬래시 명령어로 `load`를 부르게 한다. (설계서에는 예시만, 구현은 5단계)

## 11. 캐릭터 만들기 화면 (character-maker.html)

함께 전달하는 파일은 claude.ai에서 만든 **프로토타입**이다. 질문 10개(이름, 별명, 성격, 말투, 이모지, 호칭, 관계 시작점, 좋아하는 것, 예시 대사, 관계 천장)를 하나씩 묻고, 5.1 모양의 JSON을 내보낸다. 지금은 저장 없이 "복사하기"만 있고, 그 JSON을 대화창에 붙여 `save`로 등록하는 용도로 바로 쓸 수 있다.

**나무 클라우드 홈페이지로 옮길 때 요구사항:**

1. 질문 목록(`STEPS`)을 하드코딩하지 말고 서버 `character_schema`에서 받아 그린다.
2. 로그인 없이도 만들어볼 수 있게 하고, **저장할 때 로그인**하게 한다. 만들던 내용은 로그인 후에도 이어지게 (지금은 브라우저 localStorage에 임시 저장 중).
3. 저장되면 "내 AI에 연결하기" 안내로 이어진다: 사용자의 나무 MCP 주소 + claude.ai에 커넥터 추가하는 방법 + 10.1 프로젝트 지침 복사 버튼.
4. 로그인한 사용자를 위한 내 캐릭터 목록 / 고치기(기존 카드 불러와서 생성기 다시 열기) / 지우기.
5. 시작점보다 낮은 관계 천장은 고를 수 없게 하는 규칙은 프로토타입에 이미 있음. 서버에서도 같은 검사를 한다.
6. 디자인은 홈페이지 기존 톤에 맞춰 바꿔도 된다. 질문 흐름과 "답할 때마다 잎이 돋는" 아이디어만 살리면 된다.

## 12. 보안과 사생활

- 캐릭터 일기와 원문은 사적인 내용이다. 저장소가 비공개인지 확인하고 (3장 3번), 공개 저장소라면 캐릭터 그릇 쓰기를 막거나 경고한다.
- `character` 그릇은 기본 recall/search에서 제외 (7장).
- 원문은 요청 시에만 저장 (5.5).
- `forget`은 관련된 일기, 핵심 기억, 후보, 원문을 함께 지운다. GitHub 기록(커밋 이력)에 남는 문제를 어떻게 다룰지 조사해서 제안해줘 (완전 삭제가 어렵다면 사용자에게 그 한계를 알리는 문구라도).
- 표현 수위: 나무 클라우드는 여러 사람이 쓰는 서비스이므로, 나중에 수위를 여는 기능은 성인 인증 등 법적 책임이 생길 수 있다. **이번 범위에서는 구현하지 않고**, 열기 전에 별도로 법적 확인이 필요한 항목으로 남긴다.

## 13. 동시 접속

웹과 터미널에서 같은 캐릭터를 동시에 부를 수 있다.
- 일기, 후보, 원문은 **추가만** 하므로 충돌하지 않는다.
- 관계 상태는 일기에서 다시 계산하는 값이라 덮어쓰기 문제가 없다.
- 카드 수정은 버전 확인(마지막으로 읽은 버전과 다르면 거절) 방식으로 막는다.

## 14. 구현 단계

| 단계 | 내용 |
|---|---|
| 0 | 3장 사전 조사 → 허니에게 보고, 설계 차이 확정 |
| 1 | `character` 그릇 + `character_schema` + `save` / `list` / `load` (설정 글 틀 포함) |
| 2 | `diary` + 호감도 계산 + 관계 단계 + `core` (후보 → 확인) |
| 3 | `forget` + 원문 보관 + 기본 recall/search 칸막이 |
| 4 | 나무 클라우드 홈페이지에 생성기 이식 (11장) |
| 5 | 연결 안내: claude.ai 프로젝트 지침 템플릿, Claude Code용 CLAUDE.md / 슬래시 명령어 예시 |

각 단계가 끝날 때마다 나무 tasks 그릇에 기록하고 버전을 올린다 (기존 방식대로).

## 15. 완료 확인 체크리스트

- [ ] JSON 붙여넣기로 캐릭터가 등록되고 id가 부여된다
- [ ] 대화로 질문에 답하며 캐릭터를 만들 수 있다 (`schema` 사용)
- [ ] 이름과 별명 둘 다로 불러올 수 있다. 같은 이름 중복은 막힌다
- [ ] 새 대화에서 프로젝트 지침만으로 캐릭터가 불러와진다 (claude.ai에서 실제 테스트)
- [ ] 마무리 말을 하면 일기가 저장되고, 점수 변화와 이유가 남는다
- [ ] ±5를 넘는 점수 변화는 잘린다. 단계는 관계 천장을 넘지 않는다
- [ ] 핵심 기억 후보는 확인 전까지 core에 들어가지 않는다
- [ ] "잊어줘"로 지정한 기억이 일기, 핵심 기억, 원문에서 함께 지워진다
- [ ] 일반 recall/search 결과에 캐릭터 기록이 섞이지 않는다
- [ ] 웹과 터미널에서 동시에 일기를 써도 호감도가 정확히 합산된다
- [ ] `load` 결과가 크기 목표 안에 들어온다
- [ ] Claude Code(CLI)에서도 같은 캐릭터로 불러와진다
