기억은 하나, 실행 엔진은 빌려 쓴다

NAMU의 기억은 머신마다, AI마다, 그리고 기억의 종류마다 남기는 방법과 사는 곳이 다릅니다. 이 문서는 그 전체 구성을 다이어그램으로 한 장에 펼쳐, 매번 다시 묻지 않아도 되게 만든 설계도입니다.

처음이시라면 나무 안내서부터 보십시오 — 이 문서는 설계를 이미 궁금해하는 분을 위한 것입니다. 설치는 설치하기, 웹 연결은 웹에서 직접 서버 운영하기·나무 클라우드에 있습니다.

데이터 루트 ~/.namu (고정) 그릇 교훈 · 개인 사실 · 작업일지 · 쪽지 · 첨부 기록 인터페이스 MCP · 도구 15종 (웹은 11종) 검색 SQLite FTS5 · 다섯 그릇 전부 기록 3층 — 무엇을 · 왜 · 그때 동기화 Git (선택)

모든 다이어그램은 같은 4색 범례를 씁니다

01 전체상

어떤 AI가 붙어도, 바라보는 기억은 하나다

02 세 개의 축

"다르게 남긴다"는 건 세 축이 겹쳐 있다는 뜻

기억이 달라지는 방향은 딱 세 가지입니다. 이 셋은 서로 직교(independent)합니다 — 하나의 기록은 세 축의 좌표를 동시에 갖습니다. 예: "hp 머신에서 · Claude Code가 · 교훈(lesson)으로" 남긴 한 줄.

Axis A · 종류

기억의 종류 (그릇)

무엇을 기억하느냐에 따라 사는 그릇이 갈립니다. 다섯 그릇 모두 검색은 같은 색인을 타지만, 정정 방식과 recall에서 나오는 방법은 그릇마다 다릅니다.

03 그릇 (Axis A 상세)

다섯 그릇 — 성격이 다른 기억은 따로 담는다

왜 쪽지 그릇이 따로 있나: "영화 8시 20분" 같은 일회성 정보를 저장하라고 하면, 갈 곳이 없어 learnings.yaml(엔지니어링 지식베이스)로 밀려들어와 검색 품질을 떨어뜨렸습니다. namu-56에서 전용 서랍을 냈고, 이 그릇만 append-only가 아닙니다 — 떼면 파일에서 사라집니다. Git 병합도 줄 단위(union)가 아니라 파일 단위입니다. 줄 단위로 합치면 한쪽에서 뗀 메모가 다른 쪽 파일에서 되살아나기 때문입니다.

쪽지도 색인은 갖습니다(fts5-memo-tasks-index): 예전 문서에는 "쪽지는 색인 안 함"이라고 적혀 있었는데, namu-56이 금지한 것은 교훈 색인에 섞이는 것이지 색인을 갖는 것이 아니었습니다. 지금은 교훈과 분리된 자기 표를 씁니다 — 지식베이스 오염 0이라는 존재 이유는 그대로 지키면서 찾기는 빨라집니다.

첨부 기록 그릇이 다른 점: 이 그릇은 파일 자체가 아니라 이력을 담습니다. 몸통은 사용자 저장소 attach_file/에 있고 각 PC로는 안 내려옵니다. append-only라 고칠 수 없으므로 "지금 살아 있는 파일 목록"은 status(올림/새 판/지움)를 훑어 계산합니다. 상세는 07절.

검색 색인 — 다섯 그릇이 한 길로 (fts5-memo-tasks-index, 2026-08-08)

예전에는 교훈만 색인을 타고 나머지는 질의마다 파일을 통째로 읽었습니다. 지금은 다섯 그릇이 모두 SQLite 색인을 탑니다. 바꾼 근거는 성능이 아니라 통일성이었습니다 — 조회 경로가 그릇마다 갈라져 있으면 개선이 한쪽에만 닿습니다.

  • 표 구성 — 교훈은 종전의 자기 표(learnings + learnings_fts), 나머지 넷은 같은 모양의 표(bowl_<이름> + bowl_<이름>_fts, trigram)를 하나씩 갖습니다.
  • 낡음 판정 — 그릇마다 원본 파일들의 크기·수정시각을 모은 서명 하나로 봅니다. 세션 시작·서버 부팅·pull 직후에 바뀐 그릇만 다시 만듭니다. 검색 진입점에서도 한 번 더 보는데, 안 그러면 방금 남긴 기록이 다음 검색에 안 잡히는 구멍이 생깁니다.
  • 검색어 규칙 — 띄어쓴 낱말별 AND(순서 무관). 세 글자 미만 낱말이 섞이면 색인을 건너뛰고 LIKE로 전수 조회합니다 — trigram은 두 글자를 원리상 못 찾기 때문입니다.
  • 규칙은 함수로 공개한다 — db.query_tokens·db.matches_all_tokens. 색인을 못 타는 경로(클라우드의 회원별 작업일지 등)가 규칙을 베껴 가면 두 서버가 갈라지기 때문입니다. 실제로 v0.1.60에서 클라우드 작업일지만 옛 방식으로 남는 사고가 났고, v0.1.61에서 이 함수를 부르는 것으로 해소했습니다.
  • 작업 설명서도 검색 대상 — task.md 한 장이 결과 한 건으로 들어가며 tag가 설명서입니다. 다만 브리핑의 "최근 활동"과 마무리 검사에는 섞지 않습니다 — 섞으면 오늘 아무 일도 없던 작업 전부가 활동 목록에 나타납니다.
  • 첨부 기록의 금지선 — 색인 서명은 attachments.yaml 한 장만 봅니다. 사용자 저장소 attach_file/은 건드리지 않습니다(07절).

기록은 세 층으로 남는다 (namu-65)

다섯 그릇 모두 같은 3층 구조를 갖습니다. 셋 다 필수이고, 적을 것이 없으면 생략 한 단어를 넣습니다.

  • summary — 한 줄 요약(무엇을). 브리핑·목록 화면에 실리는 유일한 칸이라, 일을 한 AI가 저장 시점에 한 번 쓰고 고정합니다. 나중 세션이 볼 때마다 요약을 새로 지어내 매번 달라지던 문제를 여기서 끊습니다.
  • reason — 왜 그런가 / 어떻게 알았나. 결론만 남기면 다음 세션이 판단 근거를 몰라 같은 논의를 되풀이합니다.
  • body — 그때 무슨 일이 있었나. 원문·경위 전부, 길이 제한 없음. 이 칸이 없어서 웹에서 저장한 조사 원문이 통째로 사라진 적이 있습니다.

recall vs search — 같은 query, 다른 목적

  • recall = 작업 시작 전 맥락 로딩. "뭐라도 준다" — 매칭이 약하면 최신순으로 폴백. 붙여둔 쪽지 + profile 전체 + learnings 검색결과 + 열린 작업을 한 번에 반환.
  • search = 판단 중 패턴 분석. 정확히 매칭되는 것만, 없으면 빈 결과 + 항상 {success, failure, partial} 경향 요약 첨부.

도구는 열다섯 개 — 기억 여덟 · 첨부 일곱

기억을 다루는 도구는 namu_recall · namu_search · namu_record · namu_memo_remove · namu_task_pin · namu_task_unpin · namu_task_move · namu_sync_setup 여덟이고, 파일을 다루는 도구가 namu_upload_file · namu_list_files · namu_download_file · namu_delete_file · namu_create_upload_ticket · namu_create_download_ticket · namu_check_ticket 일곱입니다(아래 07절).

웹으로 나가는 것은 열한 개입니다 — 기억 쪽 namu_recall·namu_search·namu_record·namu_task_move 넷과 첨부 일곱 전부. 빠지는 넷(namu_memo_remove · 책갈피 둘 · namu_sync_setup)은 플러그인 전용입니다(아래 08절).

i

책갈피가 기록이 아닌 이유(namu-70): "다음엔 이것부터"는 log.md가 아니라 별도 파일 한 장(.pin.<기기>)에 적습니다. log에 적으면 ① append-only라 뗐다 붙였다를 표현할 수 없고 ② 그 작업의 최종 시각이 갱신돼 화면 순서가 두 경로로 흔들립니다. 파일을 기기마다 가르는 것이 Git 충돌 0의 근거입니다 — 각 기기는 제 파일에만 씁니다.

04 저장 지도 (Axis B 상세)

모든 것이 사는 곳: ~/.namu

PC 간 합류하는 것

learnings.yaml · profile.yaml · attachments.yaml · tasks의 log.md·task.md. .gitattributes의 merge=union + ULID 키 덕분에 오프라인 다중 PC 병합 충돌이 0. memo.yaml만 파일 단위 병합입니다 — 줄 단위로 합치면 한쪽에서 뗀 메모가 되살아나기 때문입니다.

기기에만

재생성되는 캐시

머신 (B)

분산 저장, 통합 진실

권위는 공유되는 log.md 하나입니다. PC마다 갈리는 것은 재생성 가능한 캐시(db/)와 책갈피(.pin.[machine])뿐 — 각 기기가 제 파일에만 쓰므로 Git 충돌이 0입니다. NAMU_MACHINE은 PC별로 한 번만 설정합니다.

AI (C)

엔진은 부품, 기억은 코어

기본 워커 = 메인 AI의 네이티브 서브에이전트(추가 비용 0·보안). 외부 엔진(agy·Gemini)은 설치/작업 시 고르는 override. 선택값은 namu_workers.yaml에.

불변식

실행 위치로 분기하지 않는다

어느 프로젝트·어느 엔진에서 기록하든 한 풀로 통합(namu-35). 나중에 공개 커뮤니티 풀이 생기면 task명·태그로 기계 추출하도록 설계됨.

07 첨부 파일 (namu-file-upload-download)

파일은 우리 서버가 아니라 사용자 저장소로 간다

대화 중 만들거나 손에 든 파일을 회원 본인의 GitHub 저장소에 그대로 올리고, 나중에 그 하나만 다시 받습니다. 나무 서버나 개발자 서버에 사본을 두지 않습니다. 뼈대는 셋입니다.

뼈대무엇왜 이렇게
파일은 회원 저장소로실물은 저장소의 attach_file/ 한 칸에 평평하게(하위 폴더 없음)기억과 같은 원칙 — 남의 서버에 갇히지 않는다
첨부 폴더는 각 PC에서 격리sparse-checkout으로 몸통이 안 내려온다PC가 늘어도 파일이 그 수만큼 불어나지 않는다
이력은 모든 PC에attachments.yaml(첨부 기록 그릇)"무슨 파일이 있고 왜 올렸나"는 어디서나 답한다

도구 일곱 개

도구하는 일알아둘 것
namu_upload_file파일 하나를 올리고 이력을 남긴다파일 경로 또는 글자 원문 둘 중 하나. 경로가 있으면 언제나 경로 쪽이 낫다 — 파일이 AI의 출력을 안 거친다
namu_list_files올린 파일 목록크기는 첨부 기록에서 읽는다. 저장소에 물으면 안 된다(아래 급소)
namu_download_file파일 하나를 받는다받은 일은 기록하지 않는다
namu_delete_file파일 하나를 저장소에서 뺀다왜 뺐는지가 필수. 완전 삭제가 아니다 — git 이력에는 그 이전 시점이 남는다
namu_create_upload_ticket올릴 수 있는 일회용 주소이미 파일로 있는 것은 크기·종류와 무관하게 이쪽
namu_create_download_ticket내려받을 주소회원에게 파일을 건네는 방법
namu_check_ticket파일이 도착했는지 본다회원이 "올렸어"라고 할 때
i

티켓이 있는 이유: 보통 경로는 파일 몸통이 AI의 출력을 통과합니다 — 그림·PDF 같은 것은 그 자체로 불가능하고, 큰 파일은 느리고 도중에 잘립니다. 티켓은 회원의 브라우저와 서버를 직접 잇는 일회용 주소라, 몸통이 AI를 아예 안 거칩니다. 티켓 주소는 인증 미들웨어 바깥에 섭니다 — 브라우저에는 토큰이 없고, 추측할 수 없는 티켓 번호 자체가 그 자리의 인증이기 때문입니다.

⚑

급소 — 크기를 저장소에 물으면 격리가 뚫린다. 목록을 만들 때 크기까지 함께 묻는 형태(git ls-tree -l)를 쓰면, git이 크기를 알아내려고 빠진 파일 몸통을 전부 내려받습니다. 2026-08-07 실측에서 파일 2,548개에 7분이 넘도록 안 끝나 중단했습니다. 그래서 attachments.yaml의 bytes 칸이 필수이고, 목록·검색·색인 어느 경로도 크기를 저장소에 묻지 않습니다. 이것은 되돌릴 수 없는 실수입니다 — 한 번 내려오면 그 PC에서 격리가 무너집니다.

터미널은 회원 본인의 ~/.namu 사본이 이미 그 저장소에 연결돼 있어 git 명령으로 바로 다루고(git add --sparse → commit → push → sparse-checkout reapply), 클라우드는 GitHub API를 씁니다. 올린 뒤 마지막에 격리를 다시 거는 것이 핵심입니다 — 안 하면 방금 올린 파일이 그 PC에 남아 격리가 한 칸씩 무너집니다.

상세는 첨부 파일 완료 보고서(본체 몫) · 클라우드 몫.

두 배포 형태

① 자기 PC 상시구동 + 터널(cloudflared)로 공개 HTTPS — 지금 쓰는 그 ~/.namu 그대로. ② 클라우드 컨테이너(Railway 등) — 부팅 시 GitHub에서 clone. 인증은 토큰 헤더 또는 시크릿 경로.

경로 A · 나무 클라우드

주소에 실린 개인 열쇠로 가른다

?user=열쇠로 users/[열쇠]/ 서랍에 라우팅합니다. 사이트가 발급하는 열쇠는 추측하기 어려운 긴 무작위 값(token_urlsafe(32))이라 주소를 아는 것이 곧 신분입니다 — 그래서 주소를 남에게 보이면 안 되고, 새면 내 페이지에서 폐기·재발급합니다.

경로 A · 원본

원본은 사용자 저장소에

기억의 원천은 사용자 본인의 GitHub 비공개 저장소이고, 서버가 갖는 것은 그 사본뿐입니다. 그만둘 때는 주소만 폐기하면 되고, 저장소는 원래부터 사용자 계정에 있으므로 그대로 남습니다. ?client=(어느 AI가 남겼나)는 신원과 별개 축이라 그대로 유지됩니다.

웹의 한계: 원격으로 여는 건 메모리 코어(레이어 C)뿐입니다. 자동 세션 브리핑·/namu-task·서브에이전트(레이어 B)는 Claude Code·agy 전용 글루라 웹에서 동작하지 않습니다. 도구는 15종 중 11종이 노출됩니다 — 기억 recall·record·search·task_move 넷과 첨부 7종 전부. 빠지는 넷은 플러그인 전용입니다: namu_sync_setup은 서버의 저장소 배선을 바꾸는 도구라 원격에 열면 remote 탈취로 이어지므로 원천 차단하고, 쪽지 떼기·책갈피 둘은 그 PC의 파일을 다루는 도구입니다.

작업일지는 웹에서도 됩니다. 기억 도구가 4종이라는 것과 담을 수 있는 그릇이 무엇이냐는 별개입니다 — record·recall을 통해 작업일지를 쓰고 읽을 수 있습니다. 다만 기록할 때는 어느 프로젝트인지 반드시 적어야 합니다. 터미널은 현재 폴더가 곧 프로젝트지만 웹에는 그 개념이 없기 때문입니다(조회는 생략 시 전체를 합칩니다).

09 흔들리지 않는 원칙

이 설계가 지키는 여섯 가지

01

독립성은 메모리 레이어에

인터페이스가 아니라 MCP에 포터블하게. 실행 엔진은 빌려 쓰고 교체 가능한 부품.

02

원본이 곧 기억

learnings.yaml이 진실의 원천(append-only). SQLite는 재생성 가능한 캐시일 뿐.

03

append-only 로그

learnings.yaml과 작업 log.md는 수정·삭제하지 않는다. 정정은 새 항목으로.

04

승인 게이트

워커 호출 전, 검수 fail 후 재실행 전 반드시 사용자 확인. 자동 재실행 금지.

05

판단 이유 기록

결과만이 아니라 reason(왜)까지. 근거 없는 기록은 ValueError로 차단.

06

데이터 루트 고정

~/.namu 고정 상수 — 환경변수로도 못 바꿈. 분기가 없으니 오배선도 불가능.
